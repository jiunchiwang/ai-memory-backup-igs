**定位**：跨 repo 政策/慣例強制引擎，目的是防止「多 repo 各自為政」——README/CHANGELOG/VERSION/PR/branch 命名不一致的問題。作者是自己開一整套 CI gate 給自己旗下所有 `hamanpaul/*` repo 共用。

**核心機制**
- 26 條規則（R-01~R-26），涵蓋：README 必要章節、CHANGELOG fragment 模式（避免多 PR 併發改 CHANGELOG 衝突）、VERSION 與 git tag 對齊、PR 標題走 conventional-commit、branch 命名、workflow 必須 pin 40 碼 SHA（不可用分支/短 SHA）、AI agent 慣例檔（`CLAUDE.md`/`AGENTS.md`/`GEMINI.md`）存在性與版本完整性、secret scanning、文件與程式碼的死連結偵測。
- **CI 整合**：下游 repo 在 `.github/workflows/policy-check.yml` 用 `uses: hamanpaul/paulsha-conventions/.github/workflows/reusable-policy-check.yml@<SHA>` 引用，workflow ref 和 engine ref 都強制 pin 到完整 40 字元 commit SHA（明確拒絕用 branch/短 SHA，防止上游被偷改而下游無感遭殃）。GitLab 則走 pip 套件版本比對模式。
- **本地 preflight**：`policy-preflight --repo . --pr-title ... --pr-body-file ...` 可以在推 PR 前先跑過。
- **哲學**：single-source-of-truth（每個 repo 自己 pin 版本，不自動升級）、no auto-remediation（引擎只檢查回報，不自動修，靠 SOP 自癒）。

**跟你現在這個 bridge repo 的關聯**：你這裡的 `POLICIES/` 目錄 + `.githooks/pre-push` 做的事概念上很像（因果鏈/preamble/shell-safety 政策 + push 前擋門），但 paulsha-conventions 是把這套抽成**獨立引擎、跨多 repo 共用、規則編號化、且用 CI reusable workflow 強制**，而不是單一 repo 內嵌的 hook script。如果你未來想把 bridge 的 POLICIES 慣例套用到其他專案（例如 UK slot 系列），這種「規則編號 + 引擎化 + SHA-pin」的設計是可參考模式，但目前沒有跡象顯示這與你正在做的事有直接依賴關係——純粹是你要求的研究。
