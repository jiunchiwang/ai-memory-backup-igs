# DeepSeek Harness (`dsh`) 研究報告

## 1. 概觀

**DeepSeek Harness** 是 DeepSeek AI 於 2026-08-13 發布的開源 agent harness，採 MIT 授權。核心理念是 **"Everything is a plugin"** —— 所有能力（模型、工具、技能、session、sandbox、storage、loop、排程、UI）都是可熱插拔的 plugin。

- **GitHub**：`github.com/deepseek-ai/deepseek-harness`（147k ★）
- **狀態**：Developer Preview（明言會有 breaking changes）
- **底層框架**：[Cordis](https://github.com/cordiverse/cordis) —— 一個空間時間可組合性的 plugin kernel
- **語言**：TypeScript（Node.js 22.19+ / 24+）
- **啟動指令**：`npx @deepseek-ai/dsh web`（Web UI 跑在 `127.0.0.1:3080`）

---

## 2. 核心架構

### 2.1 三層結構

| 層 | 做什麼 | 不做什麼 |
|----|-------|---------|
| **Model** | 生成 token、推理、決定呼叫哪個 tool | 不能自己開檔、跑指令、記憶上一輪 |
| **Harness (dsh)** | 給 model workspace、tool registry、sandbox、permission policy、append-only session log、agent loop | 不訓練/託管模型 |
| **Kernel (Cordis)** | 掛載/卸載 plugin、追蹤依賴、reversible effects | 不限於 agent，是泛用 plugin framework |

### 2.2 Cordis 核心概念

Cordis 論文《A Programming Paradigm for Spatiotemporal Composability》定義兩個維度：

1. **Temporal composability**：任何 effect 可完全撤銷（每個 context transformation 攜帶 inverse）
2. **Spatial composability**：跨 component 的依賴是 reactive 管理的

統一成一個 **Context type**，plugin 透過它：
- 註冊 service、tool、event listener
- 宣告 `inject` 依賴（framework 等 required service ready 才 load）
- 卸載時自動 cleanup（不需手動 removeListener）

### 2.3 Plugin 形式（三種）

```typescript
// 1. Function form（最常用）
export const name = 'my-plugin'
export const inject = ['tools']  // 依賴宣告
export function apply(ctx: Context) { ... }

// 2. Object form
export default { name: '...', inject: [...], apply(ctx) { ... } }

// 3. Class form（提供 service 時用）
export default class MyService extends Service {
  static inject = ['tools']
  constructor(ctx: Context) { super(ctx, 'myService') }
}
```

|------|------|
| **Models** | LLM adapter（DeepSeek / Anthropic / OpenAI / 自訂 OpenAI-compat endpoint） |

| **Sessions** | Append-only `SessionEvent` log，支援 resume/fork/search/replay |

| **Storage** | 持久化後端 |
| **Agent Loops** | turn 策略本身也是 plugin，換 loop ＝ 換掛載 |
| **Scheduling** | 背景任務、reminder、subagent 委派 |
| **UI** | Web client / HTTP server 都是 bundle，換 UI 不用 fork |

## 4. 四種執行模式

| Mode | 工具集 | 適用場景 |
|------|-------|---------|
| **Standard** | Full（file edit、shell、search、skills、planning、subagents、workflows） | 日常 coding |

| **Minimal** | 只有 persistent bash + str_replace_editor | 模型 benchmark（最小干擾） |
| **Creator** | Standard + runtime inspection + plugin experiment | 開發新 preset / 測 plugin |

## 5. Session 模型（Every run is traceable）

- **Append-only event stream**：所有 model-visible 的東西（system prompt、reasoning、tool call、結果、subagent scheduling、context injection）全部進 log
- **Trajectory view**：按 source 檢視
- **Model history 是 projection**：不另開 history，而是從 log 投影出來
- **Resume / Fork / Replay** 全部讀同一份 stream

---

## 6. 依賴與生命週期

### 6.1 Service 依賴

```typescript
export const inject = ['tools']  // required
// 或
const metrics = ctx.get('metrics')  // optional query
```

- Required 未 ready → plugin 等待不載入
- Service 在運行中消失 → 依賴它的 plugin 自動 dispose，service 回來後重載

### 6.2 Effect cleanup

```typescript
ctx.effect(() => {
  const timer = setInterval(...)
  return () => clearInterval(timer)  // 卸載時執行
})
```

任何透過 `ctx` 註冊的 listener/tool/timer，卸載時自動 cleanup。

### 6.3 Service 隔離

`cordis.yml` 可用 `isolate` 讓不同 plugin group 看到同名 service 的**不同 instance**。

## 7. 配置方式

- **Profile**：預設的 plugin 組合
- **Bundle**：一包 plugin 的集合
- **Patch layer**：`cordis.yml` 疊加配置，後層覆蓋前層（整 row 取代，非 deep merge）
- **載入順序**：bundle patches → profile patch → machine patch → CLI overlay

```bash
dsh web --dump-config   # 印出組合後的完整 plugin tree
dsh web --patch ./my.yml  # 疊加自訂 patch
```

## 8. 與 Bridge 的對照（借鏡評估）

| 面向 | DeepSeek Harness | telegram-kiro-bridge | 借鏡判定 |
|------|------------------|---------------------|----------|
| **擴充模型** | Cordis plugin：每個 capability 都能熱插拔＋自動 cleanup | MCP server + specialist config JSON | ⚠️ bridge 目前沒有「自動 cleanup on unload」機制 |
| **Session 持久化** | Append-only event stream，resume/fork 全部讀同一份 | JSONL transcript + session archive | ✅ 結構相似，但 bridge 的 fork 是 transcript clone 非 projection |
| **執行模式** | 四種 mode 在同一 core，差別只是 plugin 組合 | 無正式 mode 概念（/moa plan、run_plan 是隱式模式切換） | 🟡 可考慮讓 specialist preset 更 declarative |
| **Tool 註冊** | `ctx.tools.register(schema)`，schema 自動進 prompt | MCP server 暴露 tool（bridge 不直接 register，靠 agent CLI 載 MCP） | 構造不同，不直接借鏡 |
| **Sandbox** | 內建 Linux/macOS/Windows 三套沙盒，per-call policy | 無沙盒（靠 ACP adapter 自己的權限） | 🟡 可觀望，但 bridge 不是執行層 |
| **依賴 reactive** | service 消失 → 依賴者自動 dispose → service 回來自動重載 | specialist MCP wiring check 是啟動時驗、不是 reactive | ⚠️ 若未來 MCP server 熱重載，需考慮類似機制 |

### 8.1 建議吸收項目

| 項目 | 理由 | 優先級 |
|------|------|--------|
| **Effect disposal pattern** | bridge 的 MCP server / specialist 目前沒有「卸載時撤銷所有 side effect」的構造，容易洩漏 listener | 中（可不急，目前沒熱卸載需求） |
| **Declarative capability composition** | bridge 的 specialist-domains.json + acp-providers.json 已類似，但沒有 patch layer 概念 | 低（目前規模不需要） |
| **Append-only projection** | bridge 的 session archive 是複製，不是 projection；若要做 fork/branch 會是複製檔案而非 view | 低（目前 fork 需求不強） |

### 8.2 不建議吸收項目

| 項目 | 理由 |
|------|------|
| **Cordis kernel 整套** | bridge 的定位是 Telegram adapter＋orchestration，不是 plugin runtime；引入 Cordis 會改變整個架構 |
| **沙盒** | bridge 不執行程式碼，靠 ACP adapter 自己的安全模型 |
