## QM 研究摘要

### 定位

**QM** 是 Y Combinator 出品的 **multiplayer agent harness**，專為「公司級」使用場景設計（不是個人助理）。它同時支援 **Slack + Web UI** 雙端，讓公司員工各有獨立 workspace，又能在 channel/project 裡協作。

### 核心架構

```
Postgres (sessions/memory/queue)
        ↕
 Headless Core（API + policy + scheduler）
        ↕
   Agent Loop（可換 harness：Pi / OpenCode / Codex / Claude Code）
        ↕
   Per-scope Sandbox（files / tools / logged-in services）
```

- **Harness 抽象**：同一套 core 可以換底層 agent CLI（Pi、OpenCode、Codex、Claude Code），透過 `HARNESS=` 環境變數切換
- **Scope 隔離**：每個人/每個 room 有獨立的 memory、files、keychain、crons、permissions、sandbox
- **Plugins 架構**：Slack/Web UI/Admin/Portal 都是可選 plugin，透過 `plugins/chassis` 共享簽名與 HTTP helper
- **Durable by default**：不信任 process memory（藍綠部署會洗掉），所有持久狀態必須存 Postgres

### 安全模型

三種 posture（`HARNESS_SECURITY_POSTURE`）：

| Posture | 行為 |
|---------|------|
| **strict** | 每個 tool call 都暫停等人核准 |
| **auto**（預設）| classifier 篩外部資料，通過才送 model |
| **dangerous** | 無篩選、無暫停 |

另有：
- **Command policy**：預宣告的命令審核規則（如擋 `rm -rf`）
- **Credential scope**：憑證只在授權 scope 內可見
- **Audit log**：所有 security-relevant action 都記錄
- **npm 7-day cooldown**：新套件版本需 7 天熟化期才能進 lockfile（防供應鏈攻擊）

### 與 telegram-kiro-bridge 的比較

| 面向 | QM | telegram-kiro-bridge |
|------|----|-----------------------|
| 用戶規模 | 公司 org（多人 + scope 隔離） | 單人 + specialist 分身 |
| 前端 | Slack + Web UI | Telegram |
| Harness 切換 | 環境變數熱換（Pi/OpenCode/Codex/Claude） | `/agent` 切 ACP backend + `/model` 切 Direct API |
| Session 持久化 | Postgres | JSON 檔 + ACP session/load |
| Skill 系統 | scope-owned + grant 共享 + org 審核 | SKILL.md junction + 正本 repo |
| 安全 posture | 3 級（strict/auto/dangerous）| 無分級、依賴 agent 自己的 guardrail |
| Cron/排程 | 內建 `cron/` 模組 | `schedules.json` + bridge 排程 |

### 值得借鏡的點

1. **Scope 隔離思路**：如果 bridge 未來想支援多人，可參考 QM 的 per-scope workspace 設計
2. **Command Policy**：把「危險指令」列成 policy（而非依賴 agent 自己判斷）——目前 bridge 靠 agent steering + PTY 白名單，可考慮再加一層
3. **Durable by default 哲學**：「RAM 只能當 cache，不能當 source of truth」——bridge 目前部分狀態（如 specialist active map）其實是 in-memory，斷電就丟
4. **Harness 抽象層**：QM 把 agent CLI 當作可換零件，bridge 現在透過 `ACP_AGENT_COMMAND` + Provider 抽象層也在做類似的事，但 QM 更徹底（連 CLI 的差異都 normalize 掉）
5. **AGENTS.md 規範**：QM 的 AGENTS.md 寫得很精煉（zero comments policy、solve at shared layer、never self-review in authoring context），可參考更新 bridge 的 AGENTS.md

### 不太適用的地方

- QM 假設 Postgres 環境——bridge 目前是 file-based（低運維成本）
- QM 的「publish web apps」功能對單人用途過重
- 它的 Slack 整合假設 org workspace——與個人 Telegram bot 場景不同

## QM Harness 抽象層深入分析

### 1. 核心 Interface

```typescript
// harness.ts
export interface Harness {
  profile: HarnessAdapterProfile;    // 身份宣告
  turns: HarnessTurnController;       // 執行對話
  models: HarnessModelUtilities;      // 輔助功能
  tools: HarnessToolPresentation;     // tool 名稱轉換
}
```

**HarnessAdapterProfile** — 每個 harness 宣告自己的特性：
```typescript
interface HarnessAdapterProfile {
  id: string;                              // "pi" | "claude" | "opencode" | "codex"
  controlTransport: HarnessControlTransport; // "in-process" | "sdk" | "http"
  toolTransport: HarnessToolTransport;       // "in-process" | "plugin" | "in-process-mcp"
  transcriptFormat: string;                  // "pi" | "claude-agent-sdk" | "opencode"
  capabilities: ReadonlySet<HarnessCapability>; // "abort" | "steer" | "images" | "thinking-level" | "fast-mode"
}
```

**HarnessTurnController** — 核心執行介面：
```typescript
interface HarnessTurnController {
  runTurn(input: HarnessTurnInput): Promise<HarnessTurnResult>;
  close?(): Promise | void;
  resetSession?(sessionId: string): Promise | void;
}
```

**HarnessModelUtilities** — 輔助 LLM 任務：
| 方法 | 用途 |
|------|------|
| `shouldRespond?` | 偵測是否該回覆（Slack ambient listening） |
| `compactHistory?` | 壓縮對話歷史 |
| `contextTokenBudget?` | 回報可用 context 額度 |
| `oneShot?` | 單次 prompt（不帶 tool） |
| `judge?` | 用輕量 model 做分類判斷 |
| `screenSecurity?` | 安全篩選外部內容 |
| `pickAckEmoji?` | 選 emoji 反應（Slack 用） |
| `generateTitle?` | 生成對話標題 |
| `summarizeApproval?` | 摘要待審核指令 |

---

### 2. Harness Router

`harness-router.ts` 實作了 **動態路由**：

```typescript
function createHarnessRouter(
  adapters: ReadonlyMap<HarnessId, Harness>,  // 所有已註冊的 harness
  utility: Harness,                            // 共用的輔助 harness
  resolve: (input) => RuntimeChoice,           // 選擇邏輯
): Harness
```

關鍵邏輯：
1. **resolveRuntimeChoice()** — 根據 org config + scope config + turn request 決定用哪個 harness/model
2. **Session 切換處理** — 同一 session 換 harness 時，先 reset 舊的再 reset 新的
3. **Approved harness 過濾** — org admin 可限制哪些 harness 可用

---

### 3. 四個 Harness Adapter 比較

| 面向 | Pi | Claude | OpenCode | Codex |
|------|----|----|----------|-------|
| **controlTransport** | in-process | sdk | http | http |
| **toolTransport** | in-process | in-process-mcp | plugin | — |
| **底層** | `@earendil-works/pi-coding-agent` | `@anthropic-ai/claude-agent-sdk` | OpenCode CLI + HTTP server | Codex CLI |
| **capabilities** | abort, steer, images, thinking-level, fast-mode, provider-sessions | abort, steer, images, thinking-level, fast-mode | abort, steer, images, provider-sessions | — |
| **工作目錄** | 每 turn 建 tmpdir jail | 每 turn 建 tmpdir jail | 共用 jail + per-session | — |

---

### 4. Tool Bridging 機制

QM 的 tool 不是直接暴露給各 harness，而是透過 **PiTools** 統一定義後橋接：

```typescript
// pi-tools.ts
function createPiTools(ref: ToolContextRef, options: PiToolsOptions): BridgedTool[]
```

每個 harness 再做名稱轉換：
- **OpenCode**：`execute` → `workspace_execute`、`read` → `workspace_read`
- **Claude**：透過 MCP server 掛 `mcp__qm__<tool>`

這讓 **tool 定義只寫一次**，各 harness 自動適配。

---

### 5. Capability-driven 行為差異

QM 用 `capabilities` Set 做 feature flag：

```typescript
// 使用端檢查
if (harness.profile.capabilities.has("fast-mode")) {
  // 才傳 speed: "fast"
}
if (harness.profile.capabilities.has("steer")) {
  // 才允許 mid-turn 插話
}
```

這比 bridge 現在的「每個 adapter 自己硬編碼差異」更清晰。

---

### 6. 與 telegram-kiro-bridge 的對照

| 面向 | QM | telegram-kiro-bridge |
|------|----|-----------------------|
| **抽象層** | `Harness` interface + router | `Provider` interface（較薄） |
| **Tool 橋接** | PiTools → 各 harness 自動轉名 | 依賴 ACP/MCP 原生 tool |
| **Capability 宣告** | `HarnessAdapterProfile.capabilities` Set | 沒有統一宣告，各 adapter 自己處理 |
| **Model 選擇** | `resolveRuntimeChoice()` 多層級 fallback | `acp-providers.json` + `/agent` |
| **Session 隔離** | 每 turn 新 tmpdir jail | 共用 CWD |
| **輔助 LLM** | `HarnessModelUtilities` 9 個方法 | 分散在各處（local-llm.ts、embed-router.ts） |

---

### 7. 可借鏡的設計點

1. **Capability Set 宣告**
   - 現在 bridge 的 ACP adapter 能力差異（session/load、configOptions、MCP）是 ad-hoc 偵測
   - 可以像 QM 一樣，讓每個 adapter 在註冊時宣告自己的 capabilities

2. **Tool 橋接統一層**
   - 目前 bridge 的 `bridge-actions` MCP 只服務 agent→bridge 方向
   - QM 的 PiTools 是 **雙向統一**：core 定義一次、各 harness 自動適配

3. **HarnessModelUtilities 整合**
   - bridge 的輔助 LLM 功能（分類、壓縮、標題、security screen）分散在多個檔案
   - 可以像 QM 一樣收進 Provider interface

4. **tmpdir Jail 隔離**
   - QM 每個 turn 都在獨立 tmpdir 跑，防止 agent 污染其他 session
   - bridge 目前共用 CWD，理論上 agent 可以改到 bridge 的檔案（雖然有 skill 信任假設）

5. **Router 層級 Config 覆蓋**
   - QM 的 `resolveRuntimeChoice()` 有 org → scope → turn 三層覆蓋
   - bridge 的 `/agent` 只有單層（acp-providers.json），沒有 per-chat override

QM 的四個 harness 採用不同的接入方式：

| Harness | 接入方式 | 說明 |
|---------|---------|------|
| **Pi** | in-process（API） | 直接 import `@earendil-works/pi-coding-agent` SDK，跑在同一個 Node process |
| **Claude** | SDK（API） | 用 `@anthropic-ai/claude-agent-sdk`，spawn `claude` CLI binary 但透過 SDK 控制 |
| **OpenCode** | HTTP（CLI server） | spawn `opencode serve` 啟動 HTTP server，再用 `@opencode-ai/sdk` 呼叫它 |
| **Codex** | HTTP（CLI server） | 類似 OpenCode，spawn CLI 再透過 HTTP |

所以答案是 **兩者都用，視 harness 而定**：

- **Pi** 是純 API/SDK，沒有 CLI
- **Claude/OpenCode/Codex** 都是 **spawn CLI binary → CLI 開 HTTP server → QM 透過 SDK/HTTP 控制**

關鍵程式碼片段（OpenCode）：
```typescript
// opencode-harness.ts
const binary = opts.binaryPath ?? resolve(import.meta.dirname, "../../node_modules/.bin/opencode");
proc = spawn(binary, ["serve", "--hostname=127.0.0.1", `--port=${sidecarPort}`, "--log-level=ERROR"], {
  cwd: jail,
  env: cleanEnv,
  stdio: ["ignore", "pipe", "pipe"],
});
const serverUrl = await waitForServer(proc, opts.startupTimeoutMs ?? OPENCODE_STARTUP_TIMEOUT_MS);
const client = createOpencodeClient({ baseUrl: serverUrl, directory: jail });
```

Claude 的 SDK 內部也是 spawn binary：
```typescript
// claude-harness.ts
export function spawnClaudeProcess(options: SpawnOptions, identity?: { uid: number; gid: number }): SpawnedProcess {
  return spawn(options.command, options.args, {
    cwd: options.cwd,
    env: options.env,
    // ...
  });
}
```

這跟 bridge 的做法很像——bridge 也是 spawn `kiro-cli acp` / `claude --acp` 再透過 JSON-RPC over stdio 控制。差別是：
- QM 用 HTTP server mode（`serve` subcommand）
- bridge 用 stdio JSON-RPC（ACP 協定）

HTTP server mod 和 stdio JSON-RPC 差別在哪?

---

### 🤖 Assistant (上午9:06:39)

兩者都是 IPC（進程間通訊）方式，核心差異：

| 面向 | stdio JSON-RPC | HTTP server mode |
|------|----------------|------------------|
| **連線方式** | 父進程的 stdin/stdout pipe | TCP socket（localhost:port） |
| **生命週期** | 父進程 spawn 時自動建立，kill 時自動斷 | 需要等 server ready、手動管理 port |
| **多 client** | 1:1（一個 pipe 只能一個 client） | 1:N（多個 client 可同時連） |
| **協定** | JSON-RPC 2.0 over newline-delimited stream | HTTP REST 或 JSON-RPC over HTTP |
| **Debug 難度** | 較難（要 intercept stdio） | 較易（可用 curl / Postman 打） |
| **Port 衝突** | 不存在 | 要處理 port 佔用 |
| **跨機器** | 不行（pipe 是 local） | 可以（改 bind 0.0.0.0） |

### 實際差異舉例

**stdio JSON-RPC（bridge 現在用的 ACP）**
```typescript
const proc = spawn("kiro-cli", ["acp"], { stdio: ["pipe", "pipe", "inherit"] });
proc.stdin.write(JSON.stringify({ jsonrpc: "2.0", method: "session/new", id: 1 }) + "\n");
proc.stdout.on("data", chunk => /* 解析 JSON-RPC response */);
```
- 簡單、零 port 管理
- 但只能這個父進程用，別人連不進來

**HTTP server mode（QM 的 OpenCode/Claude）**
```typescript
const proc = spawn("opencode", ["serve", "--port=3000"]);
await waitForServer("http://localhost:3000"); // 等它 ready
const res = await fetch("http://localhost:3000/session", { method: "POST", body: ... });
```
- 要等 server 啟動、管理 port
- 但可以多個 client 同時打（例如 QM 的 event stream + turn request 可以併發）

### QM 為什麼選 HTTP？

1. **Event streaming** — OpenCode/Claude 用 SSE 推 streaming delta，HTTP 天生支援；stdio 要自己設計 multiplexing
2. **併發請求** — 同時 abort + steer + prompt 三個請求，HTTP 天然支援；stdio 要自己排隊
3. **Bridge plugin** — QM 的 tool bridging 是另開一個 HTTP server 讓 CLI 回打，這在 stdio 架構下做不到（見 `opencode-harness.ts` 的 `bridge = createServer(...)`)

### bridge 不換的理由

stdio JSON-RPC 對 bridge 的場景夠用：
- 單一 Telegram chat → 單一 ACP session，不需要多 client
- Streaming 靠 ACP 的 `session/update` notification，已經有
- 沒有跨機器需求（relay 是另一個 bot，不是連同一個 CLI）

要換 HTTP mode 的話要：
1. 改用 `kiro-cli serve`（如果有的話？目前沒看到）
2. 處理 port 分配
3. 改寫整個 `acpClient.ts`

成本高、收益低。

### 3. Runtime 驗證 + 動態擴充

```typescript
// src/provider/capability-resolver.ts

export async function resolveCapabilities(
  declared: AdapterProfile,
  initResult: AcpInitResult,
): Promise<ReadonlySet<AdapterCapability>> {
  const verified = new Set(declared.capabilities);
  
  // 動態驗證：宣告有但 runtime 沒有 → 移除
  if (verified.has("session-load") && !initResult.capabilities?.includes("loadSession")) {
    verified.delete("session-load");
    console.warn(`[capability] ${declared.id} declared session-load but runtime lacks it`);
  }
  
  if (verified.has("model-pin") && !initResult.configOptions?.some(o => o.id === "model")) {
    verified.delete("model-pin");
  }
  
  // 動態擴充：runtime 有但宣告沒有 → 加入（新版 CLI）
  if (!verified.has("steer") && initResult.capabilities?.includes("steer")) {
    verified.add("steer");
  }
  
  return verified;
}
```
