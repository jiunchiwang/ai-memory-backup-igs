## OpenCode ACP 深入研究

官方文件只有薄薄一頁（`opencode.ai/docs/acp`），真正的規格在原始碼裡。我把 `sst/opencode` 的 `dev` branch（v1.18.13）ACP 實作整批抓下來讀過了：`packages/opencode/src/acp/{agent,service,session,event,tool,permission,usage,error}.ts` + `cli/cmd/acp.ts`。

### 1. 執行模型：stdio 前臉 + HTTP 後腦

`opencode acp` 不是「另一個 agent 實作」，而是 opencode 自己 HTTP API 的薄轉譯層（`cli/cmd/acp.ts`）：

1. `Server.listen()` 起一個本機 HTTP server
2. `createOpencodeClient({ baseUrl: http://host:port })` 自己當自己的 client
3. stdin/stdout 包成 `ndJsonStream` → `AgentSideConnection`（用官方 `@agentclientprotocol/sdk`）

所以 ACP 層每個方法都對映成一次內部 HTTP 呼叫（`sdk.session.create/get/messages/prompt/command/abort`）。**這正好是 bridge 8/4 排除掉的那個架構**——opencode 兩者都做，因為它要同時餵 TUI、web、ACP 三種前端；bridge 只有一個 Telegram chat 對一個 session，多這層沒收益。這點反而佐證了當初的判斷。

### 2. 完整方法表（`acp/agent.ts`，這是最有價值的一頁）

實作的 `Agent` interface 全員：

| 方法 | 狀態 |
|---|---|
| `initialize` / `authenticate` | ✅ |
| `newSession` / `loadSession` / `closeSession` | ✅ |
| `listSessions` / `resumeSession` | ✅（分頁 cursor，limit 100）|
| `unstable_forkSession` | ✅（unstable 前綴）|
| `setSessionConfigOption` / `setSessionMode` / `unstable_setSessionModel` | ✅ |
| `prompt` / `cancel` | ✅ |

這比 bridge 現用的三個 adapter 都完整——`listSessions` / `fork` / `close` 是 Kiro 跟 claude-agent-acp 都沒給的。

### 3. initialize 宣告（`service.ts:112`）

```
protocolVersion: 1
agentCapabilities:
  loadSession: true
  mcpCapabilities: { http: true, sse: true }     // stdio 是 ACP baseline
  promptCapabilities: { embeddedContext: true, image: true }   // 無 audio
  sessionCapabilities: { close, fork, list, resume }
authMethods: [ "Login with opencode" ]
agentInfo: { name: "OpenCode", version: <安裝版號> }
```

有個小巧思：client 若在 `clientCapabilities._meta["terminal-auth"]` 宣告支援，opencode 會回一個可執行的登入指令（`opencode auth login`）讓編輯器直接開 terminal 跑。

### 4. 串流與工具對映

`event.ts` 訂閱 opencode 內部事件流，翻成 `session/update`：
- `agent_message_chunk` / `agent_thought_chunk` / `user_message_chunk`（reasoning 走 thought）
- `tool_call` + `tool_call_update`（含 `locations`、`rawInput`、edit 類附 diff、附圖）
- `usage_update`（`usage.ts` 算 input/output/reasoning/cache 分項 + 累計 USD 成本）
- `available_commands` / configOptions 同步

`tool.ts` 把 opencode 工具名對映成 ACP 的 `kind`：`execute / fetch / edit / search / read / think / other`。

**turn 邊界**用 `runUntilIdle()`：等內部 `status.type === "idle"` 才 resolve prompt，不是等 HTTP 回應。`stopReason` 有 `end_turn` / `cancelled` / `max_tokens` / `refusal`。`cancel` → `sdk.session.abort()`。

`permission.ts` 三選項固定：`allow_once` / `allow_always` / `reject_once`；client 沒宣告 `requestPermission` 能力時**一律 reject**（fail-closed，這個設計對）。

### 5. 對 bridge 的意涵

`configOptions` 的 id 是 `model` / `effort` / `mode`——**跟 bridge 讀 claude-agent-acp 的 shape 完全一樣**（`acpClient.ts:931` 那條路徑）。加上 `loadSession: true`，理論上 `ACP_AGENT_COMMAND=opencode acp` 可以直接插成第四個 backend，連 `/model` pin 跟 session resume 都對得上。

但有一個**確定會踩的不相容**：

```
🔵 [事實主張] opencode 的 initialize 無條件回傳非空 authMethods，
              會讓 bridge 永久誤判「需要登入」
├─ 🟢 A 級：service.ts:96-131 —— authMethod 物件無條件建構，
│         authMethods: [authMethod] 恆為長度 1；只有 _meta 隨
│         client 的 terminal-auth 能力變化，沒有任何「已登入則省略」分支
├─ 🟢 A 級：acpClient.ts:481 authRequired = authMethods.length > 0；
│         :459-462 註解記錄 claude-agent-acp 與 kiro-cli 已登入時回 []
├─ 🔴 反例檢查：若 opencode 會依登入狀態變動，initialize 內應讀 auth 狀態
│         → 實際 service.ts 的 initialize 完全沒碰任何 auth 查詢，只有
│         authenticate() 在驗 methodId。反例不成立
└─ 決策：強（A 級雙邊 + 反例通過）
```

後果：`transient-retry` 被關掉，且 prompt 失敗時會多掛一句誤導的「請先登入」。要接的話得在 `authRequired` 判定上加 per-backend 例外。誠實邊界：**這是讀碼推論，我沒實跑過 `opencode acp`**。

讀了 `resumeSession` / `forkSession` 的實作本體後，答案比方法表本身更有料——**最值得借鏡的不是「多幾個方法」，是它把 session lifecycle 切開的方式**。

### 1. load vs resume 的語意分離（最有架構價值）

原始碼實測（`service.ts`）：

| 方法 | 取歷史 | 重播給 client |
|---|---|---|
| `loadSession` | 全量（無 limit） | ✅ `replayMessages()` |
| `resumeSession` | `limit: 20` | ❌ **不重播** |
| `forkSession` | `limit: 20` | ✅ 重播 |

`resumeSession` 只讀最近 20 筆來**復原 model / variant / mode 設定**，不把歷史吐回 client。

對 bridge 的意義很直接：bridge 現在只有 `session/load`，而 load 會讓 agent 把整段歷史以 `session/update` 重播回來，所以必須拿 `replaying` 旗標把整段更新**全部丟棄**（`acpClient.ts:472`、`:732` 直接 `return`）。那個旗標是為了避免 4096 截斷、token 副作用被重放——**它存在的唯一理由是協定選錯了方法**。若走 `resume`，這個抑制 hack 結構上就不需要。

⚠️ 但別照抄 `fork`：它是 `limit: 20` + 重播，client 會看到一份被截斷的 transcript。同一份碼裡 load 全量、fork 只 20 筆，這個不一致看起來是 opencode 自己的疏漏。

### 2. `session/list` 當 resume 的 pre-flight（最實用）

現狀：bridge 存自己的 sessionId，resume 時直接賭一發 `session/load`，失敗才 fallback 開新 session（`acpClient.ts:866` 那條 stderr）。這是**靜默降級**——使用者以為續上了，其實是全新 session，只有 stderr 知道。

借鏡：先 `session/list` 比對 sessionId 還在不在 agent 側，對不上就明確告知。這跟你在 draft 修法上定的紀律同構：把靜默降級變成可觀測的否證條件，而不是事後從 log 考古。

### 3. 沒接到的兩個免費訊號

- **`usage_update`**：agent 側算好的 input/output/reasoning/cache 分項 + 累計 USD 直接推給 client。bridge 完全沒處理（grep 0 命中）——比自己估準。
- **`available_commands`**：agent 自報 slash command 清單。bridge 沒接，所以 `/help` 只列得出 bridge 自己的指令，agent 側（Claude Code 的 skills / commands）在 Telegram 端是隱形的。

### 4. `fork` → 對映 Telegram reply-context

從某條訊息分岔試另一條路、不污染主 session。bridge 現在只能 `/session new` 從零開始。這是唯一一個「新功能」而非「修現有設計」的借鏡。

### 5. meta 借鏡：capability 分層宣告

opencode 把 lifecycle 六個能力各自在 `initialize` 宣告（`sessionCapabilities: { close, fork, list, resume }`）。bridge 現在只讀 `agentCapabilities.loadSession` 一個 boolean，`sessionCapabilities` 整塊沒讀。好消息是**不需要新機制**——bridge 那條 `loadSession === true` 的 capability gate 就是現成 pattern，照樣擴展即可，而且三個現有 adapter 都不宣告這些能力，所以是純加值、不會動到既有路徑。
