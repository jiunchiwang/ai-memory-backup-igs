## 1. 它是什麼 / 不是什麼

一句話：**把 Claude Code 本身當成 library**。同一套 agent loop、同一組內建工具、同一份 context 管理，跑在你自己的 process 裡。

最常見的混淆是這四個東西，官方文件自己列了對照表：

| 你想做的事 | 該用 | 差別 |
|---|---|---|
| 要一個 agent，但不想自己寫 tool loop | **Agent SDK** | harness 由 SDK 提供，跑在你的機器 |
| 終端機互動 / 一次性任務 | Claude Code CLI | 同一個核心，介面不同 |
| 直接打 API、自己寫 loop | Client SDK（`@anthropic-ai/sdk`） | 只有 API，沒有內建工具、沒有檔案系統 |
| 長時間/非同步 agent，不想自己管 sandbox | Managed Agents（REST） | Anthropic 同時託管 loop 與 sandbox |

⚠️ **`client.beta.messages.tool_runner` ≠ Agent SDK。** 兩者都叫「幫你跑 loop」，但 Tool Runner 屬於一般 Anthropic API SDK，**只跑你自己定義的工具**，沒有內建的 Read/Write/Bash/Grep，也沒有檔案系統。判斷維度是兩個獨立問題：**誰提供 harness** vs **誰提供部署**——manual loop（都不提供）、Tool Runner（只給 loop）、Agent SDK（給完整 Claude Code harness）、Managed Agents（harness + 託管）。前三個都是你自己 host。

**只有 Python 和 TypeScript 有 library。** 其他語言官方建議把 CLI 當 subprocess 跑（`-p` + `--output-format json`）。

## 1. 權限：六階評估順序才是主體

`permissionMode` 只是六階中的**第四階**。完整順序：

```
Hooks → deny 規則 → ask 規則 → permissionMode → allow 規則 → canUseTool
```

每一階都能終結流程，這決定了很多「我明明設了卻沒生效」的問題：

| 階 | 行為 |
|---|---|
| 1. Hooks | 最先跑。**hook deny 連 `bypassPermissions` 都擋得住**。hook 回 `allow` 不會跳過後面的 deny/ask |
| 2. deny | 命中即封鎖，`bypassPermissions` 也擋 |
| 3. ask | 命中則落到 `canUseTool`，`bypassPermissions` 也照落 |
| 4. permissionMode | `bypassPermissions` 在此全批；`plan` 把寫檔類強制導回 `canUseTool` |
| 5. allow | 命中即核准 |
| 6. canUseTool | 前面都沒解決才呼叫；`dontAsk` 模式**直接跳過此階並拒絕** |

### ⚠️ 文件與實裝不符

官方 TypeScript reference 頁把 `permissionMode` 列成四個值（`default` / `bypassPermissions` / `plan` / `dontAsk`），但本機 `sdk.d.ts:2092` 是**六個**：

```typescript
export declare type PermissionMode = 'default' | 'acceptEdits' | 'bypassPermissions' | 'plan' | 'dontAsk' | 'auto';
```

`acceptEdits` 與 `auto` 在 permissions 說明頁有、在 TS reference 表格沒有。**以 `sdk.d.ts` 為準**（A 級 literal）。`auto` 是「model classifier 決定核准/拒絕」。

### 四個會咬人的陷阱

**① 裸名 `allowedTools` 會讓 `canUseTool` 被靜默跳過。** `allowedTools: ["Read"]` 等於 Read 的每一次呼叫都不經過你的回呼。SDK 會發一次 Node process warning，code 是 `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`——但那是 warning，不是錯誤。有 specifier 的（`Bash(ls *)`）不觸發，只有匹配的那些被跳過。

**② `allowedTools` 完全不限制 `bypassPermissions`。** 沒被列的工具不會被任何 allow rule 匹配，於是落到第四階被全批。`allowedTools:["Read"] + bypassPermissions` 依然放行 Bash / Write / Edit。要在 bypass 下擋東西只能用 `disallowedTools`。

**③ `disallowedTools` 裸名 vs 有 scope，語意完全不同。**

| 寫法 | 效果 |
|---|---|
| `["Bash"]` | Bash 的**工具定義從請求中移除**，Claude 看不到、無從嘗試 |
| `["Bash(rm *)"]` | Bash 還在。只有 `rm *` 被拒（**所有模式含 bypass**），其他 Bash 呼叫落到 permissionMode |
| `["*"]` | 全部工具定義移除 |

**④ `Write(path)` 規則永遠不會被匹配。** 官方原文：`Edit(path)` 規則管**所有寫檔的內建工具，含 `Write` 和 `NotebookEdit`**；而 `Write(path)` 這種規則「is never matched by the file permission checks」。想擋寫檔就寫 `Edit(...)`。

另外路徑錨點有陷阱：`Edit(//secrets/**)`（雙斜線）才是磁碟絕對路徑；`Edit(/secrets/**)`（單斜線）錨在規則來源，經 `disallowedTools` 傳入時等於錨在 session cwd——**擋不到磁碟上的 `/secrets`**。

allow rule 的 glob 只能接在 `mcp__<server>__` 之後（server 段不能有 glob）。`allowedTools:["*"]` 或 `["mcp__*"]` 會被**忽略**，只印一則 startup warning。
