## 發送方式

**HTML parse_mode（最直覺）：**
```html
<blockquote expandable>
1. 謝謝都你星巴克
2. 虎瑪碰搗
3. 提詞下得好，下班下得早
4. G不可失
5. 轉到老闆都點頭
6. 老虎自動跑
</blockquote>
```

**MarkdownV2：** 每行 `>` 開頭，最後一行結尾加 `||`
```
>1. 謝謝都你星巴克
>2. 虎瑪碰搗
>3. 提詞下得好||
```

**Raw entities：**
```json
{
  "type": "expandable_blockquote",
  "offset": 0,
  "length": 200
}
```

## 研究結論：在 bridge 支援 Expandable Blockquote

### 目前渲染架構（兩條路徑）

| 路徑 | 流程 | 格式 |
|------|------|------|
| **Rich Message（Draft mode）** | `renderDraftReply()` → markdown 原文 → `sendRichMessageDraft` → `trySendRichMessage` 持久化 | **Markdown** 直送 |
| **Placeholder（fallback）** | `renderReply()` → markdown → `markdownToHtml()` → `editMessageText` with `parse_mode: "HTML"` | 自製 **HTML** |

### 關鍵發現

1. **Rich Message 路徑已經天然支援**：`trySendRichMessage` 送的是 markdown 原文（`rich_message.markdown`），Bot API 10.1 的 Rich Markdown 相容 GFM — 如果 Telegram 的 Rich Markdown parser 認得 expandable blockquote 語法，那 agent 只要在回覆裡寫正確語法就直接生效，bridge 不用改。

2. **Placeholder/HTML 路徑不支援**：`format-html.ts` 的 `markdownToHtml()` 把 `>` 開頭行轉成 `<blockquote>...</blockquote>`，但**沒有** `expandable` 屬性。要支援需要：
   - 定義一個 markdown 語法慣例讓 agent 表達「這塊要 expandable」（例如用 `>>` 開頭、或特殊 token 標記）
   - 在 `markdownToHtml()` 裡識別並輸出 `<blockquote expandable>...</blockquote>`

3. **Bot API HTML 格式確認支援**：`<blockquote expandable>` 是 Bot API 7.3+ 的正式 HTML entity，所以 `parse_mode: "HTML"` 送出時 Telegram 會正確渲染。

### 需要改動的地方

| 組件 | 改動 | 複雜度 |
|------|------|--------|
| `format-html.ts` `markdownToHtml()` | 識別某種標記 → 輸出 `<blockquote expandable>` | 低（~10 行） |
| `telegram-ui.ts` `renderReply()` | 不需改，它只管截斷和拼接 | 無 |
| `telegram-rich-renderer.ts` | 不需改，Rich path 送 markdown 原文 | 無 |
| Agent 端（prompt/preamble） | 告訴 agent 可用的語法 | 文件 |

### 設計決策點

**怎麼讓 agent 標記「這塊要收合」？**

- **方案 A**：沿用 Bot API MarkdownV2 的慣例 — 結尾 `||` 代表 expandable
  ```
  >第一行
  >第二行
  >第三行||
  ```
  優點：跟 Telegram 官方語法一致。缺點：Rich Markdown 路徑可能已經認這個語法（待確認），但 HTML 路徑需要自己 parse。

- **方案 B**：自訂 token 標記，例如 `>>>expandable` 開頭
  ```
  >>>expandable
  >第一行
  >第二行
  ```
  優點：明確。缺點：非標準。

- **方案 C**：所有超過 N 行的 blockquote 自動 expandable
  優點：agent 不用學新語法。缺點：不夠精確，短 quote 也可能想收合。

### 額外考量

- **Streaming 階段的 thinking block**（`> 💭 ...`）目前只出現在 streaming 中途、turn 結束前就移除了，不影響。
- **4096 字元限制**：expandable blockquote 可以放很長內容但不影響計算（Telegram 計算 entity 長度時是算完整文字），所以截斷邏輯不變。
- **Draft 模式是否直接支援**：需要實測 `sendRichMessageDraft` 的 Rich Markdown 是否認得 `||` expandable 語法——如果認得，那 draft 路徑零改動。

### 建議實作順序

1. 先實測 Rich Markdown 路徑是否天然認 expandable 語法（發一則含 `>line||` 的 rich message 看效果）
2. 若 Rich path 已支援 → 只需改 HTML fallback path（`format-html.ts`）
3. 若 Rich path 不支援 → 兩條路都要改，統一用方案 A 語法

## 測試結論（基於 Bot API 文檔確認）

### ✅ 確認支援的三種發送方式

**1. HTML parse_mode（`sendMessage`）— 完整支援**
```html
<blockquote expandable>內容...</blockquote>
```
文檔明確列在 HTML style formatting 裡。

**2. MarkdownV2 parse_mode（`sendMessage`）— 完整支援**
```
**>第一行（expandable 以 empty bold entity 跟前面的普通 blockquote 分隔）
>第二行
>最後一行 + expandability mark||
```
關鍵語法：結尾加 `||` 標記為 expandable。注意需要用 `**>` 開頭（empty bold entity）來跟前面的普通 blockquote 分隔。

**3. Rich Message（Bot API 10.1 `sendRichMessage`）**
Rich Markdown 接受的格式跟 MarkdownV2 不完全相同——它有自己的一套 Rich Markdown/Rich HTML。Rich HTML 用 `<details>` 標籤（`RichBlockDetails`），有 `summary` + 可展開 `blocks`，這其實是比 expandable blockquote **更強大**的功能（有標題摘要行）。

但 Rich Message 的 `<blockquote>` **沒有** expandable 屬性——它用 `<details>` 取代了這個功能。

### 🔑 關鍵發現：Rich Message 有 `<details>` 可用

Bot API 10.1 的 `RichBlockDetails` 比 expandable blockquote 更好：

```html
<details>
<summary>虎機：本周三晚上 18:30 - 20:30</summary>
<p>1. 謝謝都你星巴克</p>
<p>2. 虎瑪碰搗</p>
<p>3. 提詞下得好</p>
</details>
```

- 有可見的 **summary 標題**（永遠顯示）
- 展開後看到 blocks 內容
- `is_open: true` 可以預設展開

### 對 Bridge 的影響分析

| 路徑 | 目前狀態 | 要做什麼 |
|------|---------|---------|
| **Rich Message（Draft mode）** | 送 raw markdown → Telegram 解析 | Rich Markdown 已認 `>...\|\|` 語法（待實測確認），或改用 `<details>` HTML。**可能零改動** |
| **HTML fallback** | `markdownToHtml()` 只輸出 `<blockquote>` | 需識別 `>...\|\|` 結尾並輸出 `<blockquote expandable>` |

### 限制

- `blockquote` 和 `expandable_blockquote` **不能巢狀**（API 文檔明確說明）
- Legacy `Markdown` parse_mode（非 V2）**不支援** expandable blockquote
- Bridge 目前 agent 的 thinking preview 用 `> ` 開頭行但 turn 結束前就清掉了，不會衝突

### 結論

1. **Rich Message path**（bridge 預設）：大概率已天然支援 `>...\|\|` expandable 語法，因為 `sendRichMessage` 的 Rich Markdown 基本上是 MarkdownV2 的超集。另外 Rich Message 還有更強的 `<details>` 可用。
2. **HTML fallback path**：需要在 `format-html.ts` 加 ~10 行識別 `||` 結尾的 blockquote 群組。
3. **唯一不確定**的是 Rich Markdown 是否認 `||` — 需要實際發一則確認（我目前沒有 bot token 可以打 API）。
