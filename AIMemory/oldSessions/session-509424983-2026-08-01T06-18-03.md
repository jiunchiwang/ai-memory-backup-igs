## `truncateTail` 問題分析摘要

### 根因
`truncateTail` 是「尾部保留」的滑動視窗：超過 ~3900 字時，**丟掉頭部、在開頭插 "…"**。

```
幀 N  : "很長的內容...ABC"     (3899 字)
幀 N+1: "…（丟頭）...ABCDE"    (~3900 字，頭部變成 "…")
```

Draft client 動畫是「立即顯示前 strlen(prev) 字元」，幀 N+1 頭部變了 → 共同前綴從 3899 驟降到 1 → **整段重繪**。

一旦觸發，**後續每幀都會重播**（視窗持續滑動）。

### 與已修成因的關係

| 成因 | 狀態 | 觸發條件 |
|---|---|---|
| 游標 ▍ | ✅ 已修 | 所有幀 |
| token 縮回 | ✅ 已修 | `<<TOKEN` 片段 |
| **truncateTail 滑動** | ⏸ 未處理 | **>3900 字** |

### 可能修法

| 方向 | 做法 | 優缺點 |
|---|---|---|
| **B 凍結** | 到上限就停止更新 draft | 簡單；後半段看不到 streaming |
| **D 雙層** | Draft 只渲染頭部 + "…（生成中）" | 頭部恆定；使用者知道有更多 |
| **拆訊息** | 到上限切新 draft | 複雜；破壞 draft lifecycle |
| **頭部截斷** | 丟尾巴而非丟頭 | 看不到最新內容 |

## 網路研究結果：Draft Streaming 長文處理方案

### 業界現有方案

#### 1. **grammY `@grammyjs/stream` — 自動分割多訊息**

核心做法：**超過 4096 字就自動開新的 draft_id，變成多則訊息**

```typescript
// 關鍵邏輯（from stream.ts）
if (draft_id !== undefined) {
  currentDraftId = draft_id;
} else if (currentByteCount + addedLength > 4096) {
  currentDraftId++;  // 超過上限就換下一則訊息
}
```

特點：
- 每個 chunk **不會被切開**（individual chunks are never split up）
- 超過 4096 時，**先 finalize 當前 draft（sendMessage）、再開新 draft**
- API 呼叫序列範例（6 個 1000 字 chunk）：
  1. `sendMessageDraft` → 2. `sendMessageDraft` → 3. `sendMessageDraft` → 4. `sendMessageDraft` 
  5. **`sendMessage`** (finalize 第一則)
  6. `sendMessageDraft` → 7. `sendMessageDraft` 
  8. **`sendMessage`** (finalize 第二則)
- 強烈建議搭配 `auto-retry` plugin

**優點**：完整內容、多則訊息、append-only 不變式自然維持（每則 <4096）
**缺點**：長回覆會變成多則訊息（對某些 UX 場景不理想）

#### 2. **grammY Rich Message 路徑**

`replyWithMarkdownStream` / `replyWithHtmlStream` 走的是 `sendRichMessageDraft` → `sendRichMessage`，**沒有自動分割**——它假設單則 Rich Message 就足夠，超長時會怎樣文檔沒說（可能是 API 層 truncate 或報錯）。

#### 3. **GramIO `@gramio/split` — Entity-aware 分割**

專門處理「超過 4096 後如何正確分割 entities」：
- 跨邊界的 entity 會被正確拆成兩半（offset/length 重算）
- **不是 streaming 用**，是 final send 用的 splitter

### 與我們 `truncateTail` 問題的對照

| 方案 | grammY stream 做法 | 我們目前做法 |
|---|---|---|
| 超過 4096 時 | **開新訊息** | **滑動視窗截頭** |
| 單則訊息 | 最多 4096 | 最多 4096，但頭部會變 |
| append-only | ✅ 每則 <4096 自然維持 | ❌ 頭部 "…" 破壞 |

### 可行修法方向（更新）

| 方向 | 做法 | 來源 |
|---|---|---|
| **E：採 grammY 做法** | 超過上限就 finalize 當前 draft + 開新 draft，變多則訊息 | grammY stream plugin |
| **B：凍結** | 到上限停止更新 draft，final 帶完整 | 原方案 |
| **D：雙層** | Draft 只渲染頭部 ~3800 + "…（生成中）" | 原方案 |
| **F：頭部錨定** | 改成丟尾巴而非丟頭（但看不到最新） | — |

### 建議

**方向 E（grammY 做法）** 是業界標準，優點：
1. 完整內容不丟
2. append-only 自然維持
3. 有成熟參考實作

缺點是「長回覆變多則訊息」——但這可能是可接受的 trade-off，因為：
- 使用者習慣 LLM 的長回覆（ChatGPT/Claude 都會超長）
- 多則訊息至少內容完整
- 比起「單則但整段重播抖動」，UX 可能更好<<SKILL_USED:ms-telegram-bot-rate-limit-survival|研究 draft streaming 長文處理時參考了 grammY auto-retry 與 rate limit 相關機制>>
