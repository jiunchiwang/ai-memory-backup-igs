為何有時bridge的streaming在工具訊息更新時會再重頭顯示

---

### 🤖 Assistant (下午12:59:34)

我來查 bridge 的 streaming 實作。這是讀 code 得到的診斷（沒做 runtime 重現），主因跟你在哪條 streaming 路徑上有關。私聊預設走 **draft 模式**（`TG_DRAFT_ENABLED`、`TG_RICH_STREAM_ENABLED` 預設都是 1，`src/config.ts:346-355`）。

## 核心原因：Telegram 的 live draft 是「純 append-only 動畫」

Telegram client 對 draft 更新的動畫語意是**長度差**：立即顯示新文字的前 `strlen(prev)` 個字元，只淡入多出來的尾巴（`src/telegram-ui.ts:488-494`）。所以只要 client 端「前一幀狀態」不見了，或內容在頭部被插入，它就沒辦法只補尾巴 → 整段重播。

## #1 主嫌：status 訊息第一次建立會把 draft 清掉

tool/thinking 進度是**獨立的一般訊息**，不在 draft 裡（刻意拆的，避免 volatile 內容讓 draft 抖）。第一次有 tool 狀態時走 `sendMessage`：

- `src/run-prompt.ts:638` — `ctx.api.sendMessage(chatId, content, ...)`
- Telegram 規則：chat 收到任何一般訊息 → 立即清掉該 chat 的 live draft
- 所以 bridge 馬上用同一個 draftId 重送全文補救（`run-prompt.ts:646-652`）

補救有效（內容回來了），但 client 已經沒有前一幀 → 動畫從 0 開始 → **整段回覆重頭跑一次**。

這正好解釋「有時」：只有 status 訊息**首次建立**走 `sendMessage`，之後的 tool 更新走 `editMessageText`（`:654`），一般訊息的 edit 是整則重繪、不清 draft，就不會重播。所以每個 turn 通常只在「第一個 tool 開始跑」那一刻抖一次。

額外重犯點：status 訊息被你手動刪掉、或 edit 撞 400 → `statusMsgId` 被重置（`:661-663`）→ 下一 tick 又 `sendMessage` 一次 → 又重播一次。

## #2 次因：draft 30s TTL 過期

draft 是 ephemeral。長 tool 執行期間沒有新文字 chunk 就不會觸發 `editNow`，keepalive 每 10s 補送（`:768-779`），但它在 rate limit 期間直接 early return（`:772`）。撞到 429 又剛好在跑長 tool → 30s 內沒人續命 → draft 消失 → 恢復後整段重現。程式碼註解 `:764-767` 自己記錄了這個現象。

## #3：降級路徑本來就會整段重畫

`trySendDraft` 失敗 → 刪掉 status 訊息 + `sendMessage` 重貼全文建 placeholder（`:700-724`），或已有 placeholder 時清空 `lastRendered`（`:729`）強制全量重送。

## #4：非 draft 路徑（群組 / draft 關閉）另一個機制

`renderReply` 把 tool 行放在 **body 前面**（`src/telegram-ui.ts:443-444`、`:476`：`header + tools + thinkingBlock + body + cursor`），而 rich stream edit 走 `tryEditRichMessageDraft`（`run-prompt.ts:746`）也是全量替換 + 動畫過渡。tool 行一變（新增一行、emoji 翻轉、秒數遞增）就是**頭部插入**，後面全部位移 → 長度差動畫對不上 → 整則重播。

draft path 為了避開這點才把 volatile 區拆成獨立 status 訊息；placeholder + rich stream 這條路徑沒拆，所以每次 tool 行變動都會抖，比 draft path 頻繁。
