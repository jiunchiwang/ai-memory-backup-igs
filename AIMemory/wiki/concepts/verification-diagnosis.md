# 驗證與診斷方法論

## 概述

這一頁蒐集的是**跨專案的驗證／診斷方法論**——不綁 bridge、不綁 slot，講的是「怎麼確定你的驗證真的在驗東西」「怎麼設計一個問得出答案的實驗」。2026-08-01 的 topic review 從 misc 拆出來，因為這批 facts 反覆出現、彼此互相引用，而放在 misc 等於沒有分類。

貫穿全部條目的一句話：**綠燈與陰性結果的資訊量，取決於它有沒有可能是紅的／陽性的。** 不會紅的閘門、沒有陽性對照的實驗，兩者都給你「一切正常」的錯覺。

已升格為可執行 skill：`ms-vacuous-test-gate`（閘門那半）、`ms-cross-model-adversarial-review`（異源覆核那半）。本頁保留 facts 層的實證與脈絡。

## 一、綠燈假象（閘門看起來過了但什麼都沒驗）

### 恆真斷言

若測試驗的是「經過正規化／截斷／clamp 之後的結果符合上限」，那個斷言**永遠會綠**——因為該函式本身就保證上限。必須驗**未經處理的原始值**。

實證：bridge 的 `check-bot-command-descriptions.mjs` 驗 `truncateBotCommandDescription(x)` 結果 ≤256，於是 `/dream` 的 desc 276 字元被無聲截掉尾巴 20 字，測試卻全綠不知多久。

### 期望值硬寫

「計數類漂移」的機械閘門，期望值必須當場從真實來源算出、**絕不可硬寫**，否則閘門自己會變成下一個過期來源。尤其陰險的是：**閘門本身加入後就會改變它要驗的數字**（加 `scripts/check-doc-sync.mjs` 使 smoke fast 92→93、full 95→96，所以支數改向 `run-smoke-suite.mjs --list` 動態取得）。同一組計數當時散在 10 個檔案，只改部分會讓 repo 內部互相矛盾、比全錯更難察覺。詳見 [[bridge-smoke-gate]]。

### 破法：突變測試

驗證新增斷言「真的有跑到」的手法是**突變測試**：對每一種預期壞法各做一次最小突變、確認測試分別紅，再還原複驗綠。理由是 smoke runner 只印每支腳本的 `ok`，**通過本身無法證明新斷言被執行**（2026-07-31 bridge 4 種突變逐一實證）。

**Windows Git Bash 突變測試陷阱**：不要用 `/tmp` 存備份——`cp` 會成功（Git Bash 有虛擬映射），但 node 收到字面路徑會解析成 `G:\tmp` 而 ENOENT，於是突變根本沒寫進檔案、測試對未突變原檔跑出「1/1 passed」的假綠。改用 repo 內相對路徑（`./.rp.bak`）後三條斷言才各自如預期變紅（2026-08-01 實證）。

**`tsc` 紅了不等於 dist 沒更新**：telegram-kiro-bridge 的 `npx tsc -p .` 在 `noUnusedLocals` 報 TS6133 時**仍然會 emit dist**——做突變測試時一律要 `grep dist` 確認突變真的進了產物才採信 smoke 結果，不可用 `tsc` 的 exit code 反推（2026-08-06 Fable5 覆核順帶發現）。反向的坑同一天也踩到過：突變寫成 `if (false && …)` 讓 tsc 型別收窄而**真的**編譯失敗，dist 沒更新，smoke 跑的是舊產物假綠——兩者外觀相似（都跟 tsc 的紅/綠有關）但機制相反，不能用同一條規則判斷。

### 順序型承重不變式的三件套

當要保護的是「A 必須排在 B 之前」這類順序不變式：

1. **模組契約測試** — fake api 記錄 send/edit/delete 呼叫序列
2. **來源順序斷言** — `indexOf(A) < indexOf(B)`，錨在該呼叫點**獨有**的字串上避免多處 match
3. **mutation test** — 手動把呼叫搬到錯位置確認測試真的紅，再還原並 `git diff` 確認無殘留

這三件套是對抗恆真斷言的具體做法。

## 二、診斷實驗的設計原則

2026-07-31 的 draft 重播診斷連續踩到三條，每一條都讓一整輪實驗作廢：

| 原則 | 踩坑實況 |
|---|---|
| **陰性結果必須有有效的陽性對照才可解讀** | 對照臂（已知會清 draft 的 `sendMessage`）也是陰性 → 處理臂的陰性零資訊量，不能拿去宣稱假設為假 |
| **設計觀測前先確認 observable 跟症狀是同一件事** | 症狀是「消失**再重播**」，我卻去問「是否消失」→ 三臂全白測 |
| **症狀若是內容相依的，就不能把「內容型態」固定不變** | 五臂全用純文字變其他軸，而症狀實際跟 markdown／長度有關——固定錯的變數，做多少臂都是負的 |

第三條的推論：**八臂全負代表「用 raw API 重建的路徑都重現不出症狀」，不代表症狀不存在。** 這種時候正解是停止重建、改在生產側落內容快照抓真實的前後兩幀，而不是再猜第九個維度。相關結論見 [[bridge-streaming]]。

### 單變數探針全負時的交集盲點（2026-08-01 補充）

當一連串單變數探針全部回負，要懷疑**真兇是「兩個變數的交集」**而不是再多加單軸的臂——把已測過的臂按變數排成 2×2 表，通常會發現每支探針都把對方的變數 held constant，**交集那格從沒被測過**。

實例：frames 探針測「同內容重送」但間隔壓到 4s、ttl2 探針「拉長間隔」但內容是 append，於是紅格（同內容 × 20s 間隔）因此漏掉——而那正是 keepalive 閃爍的根因。

另一個可重用的量測判準（2026-07-26 背景通知 flakiness）：**調整等待延遲後時間差不變，就不是競態**——這條讓一個錯誤的 race condition 假設被推翻，修復方向改往投遞路徑。

### 拿模型當受試者時：先量底噪，再談差值（2026-08-12）

用 fixture 比較兩個模型（或兩種呈現條件）的能力時，**零改動重跑一次同一組題目**是必要的第一步。
2026-08-12 的 code-review 對照實驗這樣做之後量到 **test-retest 翻轉率 25%**：8 題的 orig 條件
什麼都沒改重跑，16 個 cell 翻了 4 個，且四次全部同方向。n=8 的一臂光噪音就有約 ±1.4 題擺盪
∴ 該實驗先前所有「誰多幾題」的結論全部落在噪音帶內。

- **判準**：n≤8 的 fixture 比較，沒有底噪估計就不要解讀差值。
- **同方向的翻轉要標記**：四次同向可能是運氣（純隨機 p=0.125），也可能是伺服器端版本／負載的
  批次效應——單靠這種實驗**無法區分**，要誠實寫成未解。
- **評分尺必須逐字寫進產出物**。同一批答案在不同 session 用不同尺評，差了 3 題（9/16 → 6/16）。
  跨批次比較前要把舊批與新批**在同一輪、同一把尺下重評**，否則量到的是評分者漂移。
- **機械抽取式要用真實回答校準**：從 `行 N` / `第 N 行` 兩式起手，讀真實答案才發現漏了
  `584–587行：`（數字在前）與 `124–131：`（純數字加冒號），造成假漏報。憑想像列舉格式必有盲區。

### fixture 的「移除」動作會留下可被受試者讀出的痕跡

同一實驗的對照組是「剝掉註解」，但剝完保留原行號 ∴ 行號不連續，兩個模型都把空洞讀成
「有程式碼被刻意隱藏」並開始推測那幾行的內容（其中一次虛構出「行 289-290 是 rawSteps 的
初始化」並據此棄答）——漏報被系統性放大，且與「沒有註解可讀」混在一起無法分離。

修法是**剝完連續重編行號**（不要用空白行占位並在 prompt 解釋，那會引入 meta-awareness）。
2026-08-12 修完重跑的結果值得記：**偽影確實消失了**（虛構內部隱藏行的行為不再出現，
只剩對片段邊界之外的合理推測），**但修掉它並沒有換到可辨識的改善**——剝註解組的提升
完全落在同批零改動組的漂移量內。∴ 已知偽影該修，但不要預設修掉它就會解釋掉觀察到的差異。
完整數據見 [[bridge-model-strategy]]。

### 註解本身就是答案洩漏（2026-08-11）

拿本 repo 的碼片段當「找 bug」fixture 時要注意：本 repo 註解密度高，幾乎每個不變式旁都寫了
「為什麼」。2026-08-12 的模型對照實驗中，**5 次命中全部落在有註解點出不變式的題目**，
註解乾淨的兩題兩臂皆 0 命中。∴ 用註解密集的碼去評估覆核者能力會系統性高估它——設計這類
fixture 要至少各半（有／無註解洩漏）並分開計分，否則量到的是「會不會讀註解」而不是
「能不能推導缺陷」。

### 行為測試 vs 模型冷讀：兩條可操作判準（2026-08-12）

同一組 8 個真實缺陷，讓 repo 既有的 mutate-gate 行為閘門與模型冷讀分別偵測：閘門 8/8
killed 且每條都紅在目標 check；模型命中率 0/8 到 8/8 不等，外加約 25% 的 run-to-run 噪音
（見上一節底噪量測）。⚠️ 這**不能**宣稱「行為測試比模型會找 bug」——閘門本來就是為這些
變異寫的、模型是冷讀，8/8 是構造上的。能宣稱的是對**已枚舉**的缺陷，行為測試給確定性偵測，
模型給機率性偵測。可操作判準有兩條：

1. **缺陷若「與標準樣板同形但參數處理被動過手腳」**（實例：`Math.max(1, Math.floor(limit) || 1)`
   被改成 `limit`，少夾下界）——模型覆核期望值是 0，16 個回答全漏且全部在同一檔案誤報另一個
   不存在的缺陷，加派覆核者不會改善（同源天花板）。**這類不變式必須有行為閘門。**
2. **缺陷若是「碼內自相矛盾」**（相鄰三行用不同陣列、計數器只增不減）——模型 8/8 全中，
   是覆核甜蜜區，不必優先寫閘門。

## 三、證據的時效與邊界

- **診斷證據必須在 restart／recovery 邊界失效**：recovery 之後若沿用 pre-recovery 的 API error 記錄，真正的 post-recovery 卡死會誤用陳舊錯誤當根因而誤診。∴ recovery 時要主動清除舊錯誤證據。
- **重現 restart 後的視窗溢出／狀態殘留類 bug**，最有效的手法是拿**真實 transcript 重播**（real transcript replay），比造合成輸入更容易踩到真實邊界條件。
- **放行閘要機械化而非主觀判斷**：依賴套件大版本升級前先 grep 全部 `.ts/.mjs` 確認零 import 指向已移除的模組（例如 MCP SDK 的 HTTP/SSE transport），零命中才放行 push。

## 四、可觀測性：純觀測欄位等於沒有訊號

**只有測試讀、生產無人消費的欄位，等於沒有 runtime 訊號。** 這類欄位應在生產路徑落 log，讓問題在真實流量中自己曝光；否則 regression 復發時完全無聲（2026-07-31 bridge 的 `lateCreates` 實證——它原本只有 smoke 讀得到）。

延伸的另一半在 [[bridge-project]]：落了 log 也不等於看得到——`console.warn` 只存在於 supervisor 終端的 scrollback，關窗即失。凡需要事後比對時間戳的診斷，都必須自己落檔。

## 五、型別與測試都看不見的缺陷型態

**在原本全同步的路徑中插入一個 `await`，就等於自己開了 finalize/cancel race 縫。** `coalesceAsyncRunner` 的 `isCancelled` 只在入口與補跑前檢查，fn 執行中翻轉完全攔不住——所有呼叫端的入口 guard 看起來像已保護到，其實一個都擋不住 mid-run。修法是 await 回來後對 finalize flag 再檢一次。

這類缺陷在**型別、既有測試、API 回傳值上全都看不出來**，只有異源覆核或人工讀時序抓得到（2026-07-31 bridge F1 實證）。

## 六、同源自審的天花板

bridge 覆核鏈三輪實證同一個失效模式：**「我寫的因果宣稱與程式碼實際時序不符」**——

1. 第一輪：AI.md／註解／commit message 三處共用同一個錯敘事（`<<RESTART>>` 的 finally 時序）
2. 第二輪：修正版**又寫錯**（「5 條呼叫端都是 await → 同步 exit」實際只 2 條）
3. 第三輪：錯**長在測試裡**（測試的 resolver 被救援 delete 蓋掉，drain 其實走 1.5s 逾時放生，斷言仍全綠）

共同根因是從意圖推理而非讀實際呼叫順序，且同源自審看不出來（三處都是同一人寫的，互相印證只是回音）。

防法兩條：① 凡寫「因為 X 所以 Y」先讀 X 的實際時序 ② **測試的敘事也要用可觀測量鎖死**（如 `elapsed < deadline` 上界斷言 + 非恆真前置斷言），不能只看斷言綠。

此模式已升格為 bridge `.claudedocs/records/問題追蹤.md` 的長期警惕模式 **#002**（2026-07-31 使用者確認），涵蓋註解／AI.md／commit message／測試敘事四類高風險位置。

## 七、否定式主張的幻覺風險（2026-08-07）

GitHub tree API 的 `?recursive=1` 回應被截斷時，**WebFetch 背後的小模型會對「存在性」問題自信地答 no**——當天它連答「無 pyproject.toml／無 paulsha_cortex/／無 tests/」，一度讓我推論出「這個 repo 只有文件沒有程式碼」，足以推翻整份評估。

### 翻案手法

| 方法 | 訊號特性 |
|---|---|
| **raw.githubusercontent.com 打檔案 URL** | 存在→回檔案內容，不存在→404: Not Found。二元探針，不經摘要判斷，抗幻覺 |
| **git/trees/main:\<path\>**（不遞迴） | JSON 夠小不會截斷，可靠列出子目錄 |

### 教訓

**對「某某東西不存在」這類否定式主張，永遠要用探針覆核而非採信摘要。** 這是既有 `research-report-citations-unverified` 教訓（引用越像真的越要先查）的反向補完——引用告訴你「有」要查，摘要告訴你「沒有」也要查。
