# 突變測試：證明斷言真的會紅

2026-08-21 從 [[verification-diagnosis]]（原 202 行）與 [[bridge-smoke-gate]]（原 204 行）合併拆出——兩頁各記了一半，重複的部分（Windows `/tmp` 陷阱、順序不變式三件套）在兩邊都有一份而內容不完全一致。`POLICIES/development-methodology.md:136` 早就把 `gate-mutation-testing` 列為「跨閉環高頻模式的代表頁」，但這一頁在此之前不存在。

**核心命題**：測試綠燈不證明斷言被執行到。smoke runner 只印每支腳本的 `ok`，通過本身無法區分「斷言驗過了」與「斷言根本沒跑」。唯一能區分的操作是**對每一種預期壞法各做一次最小突變、確認測試分別紅，再還原複驗綠**（2026-07-31 bridge 4 種突變逐一實證）。

## 執行前提：突變本身會靜默沒套用

「突變步驟自己失敗」與「斷言有效」**在畫面上完全同形**——兩者都是綠燈。∴ 順序不能反：先證明突變真的發生，才有資格解讀顏色。

四個已實證的靜默失效機制（全部在 Windows／Git Bash）：

| 機制 | 症狀 | 實證 |
|---|---|---|
| `/tmp` 存突變備份 | `cp` 成功（Git Bash 有虛擬映射），但 Node 收到字面路徑解析成 `G:\tmp` 而 ENOENT ⇒ 突變根本沒寫進檔案，測試對**未突變原檔**跑出「1/1 passed」假綠 | 2026-08-01；改用 repo 內相對路徑 `./.rp.bak` 後三條斷言才各自如預期變紅 |
| regex 錨在 `\n` | 對 **CRLF 檔案比對不到** ⇒ 檔案沒改、閘門綠 | 2026-08-16 |
| shell 吃掉轉義序列 | `\\s` → `s` ⇒ 改到了**另一條**斷言，紅的不是你要驗的那條 | 同上；一條斷言花三次嘗試才隔離成功 |
| `tsc` 紅但 dist 已 emit | `noUnusedLocals` 報 TS6133 時 `npx tsc -p .` **仍然會 emit** ⇒ 不能用 tsc 的 exit code 反推 dist 狀態 | 2026-08-06。**反向的坑同一天也踩到**：突變寫成 `if (false && …)` 讓 tsc 型別收窄而**真的**編譯失敗、dist 沒更新，smoke 跑舊產物假綠——兩者外觀相似（都跟 tsc 紅綠有關）機制相反，不可用同一條規則判斷 |

∴ 三道檢查：①`grep` 確認目標文字**真的變了**（次數 1→0）；②確認紅的是**預期那一條**斷言而非別條；③最強的證據是**失敗訊息裡直接出現突變痕跡**，那證明它被執行到。Windows 上優先改用免轉義的等價寫法（如 `split("\t")[0]`）。突變測試後一律 `grep dist` 確認突變真的進了產物才採信 smoke 結果。

## 突變存活的三種解釋（不要預設是第一種）

診斷順序固定：**先問「突變真的套用了嗎」→ 再問「有沒有別的機制先攔下它」→ 最後才是覆蓋缺口**。順序反了會錯殺測試或錯放死碼。

1. **測試太弱**（唯一該補斷言的情況）
2. **等價突變** —— 突變後語意不變。實例：`positiveIntOr` 拿掉 `Number.isFinite` 的突變存活，先驗證字串出現次數 1→0、程式碼可見已改，才確認下界 `>0` 與上界 `<=max` 已涵蓋 NaN/±Infinity（`Math.floor(NaN)>0` 為 false、`Infinity<=max` 為 false）∴ 那一行是死碼，處置是**刪除**不是補斷言。
3. **防禦深度**（2026-08-19） —— 閘門沒有洞，只是另一個機制先攔下了。實例：把 `git-sha` 的 `{40}` 放寬成 `{40,}` 存活，因為 `long-hex-41` 排在它前面且兩個邊界都套、64 位 hex 先被攔下。這時要**換一個真的造得出缺陷的突變**，不是把斷言改鬆去遷就它。

## 突變體設計判準

- **「唯一失敗方式是 tsc 編譯失敗」的突變體要移出 runtime 突變集**：若一個突變體存活的唯一原因是它讓 TypeScript 編譯失敗（tsc 紅、runtime 測試從沒機會跑），代表那個不變式**已經由型別系統守住了**。正確處置是移除，不是當覆蓋缺口去補斷言——`acp-retry-telemetry` 突變集就是這樣拿掉一條針對 `EVENT_TYPES` 註冊的突變。
- **突變體撞 `noUnusedLocals` 會被判 error 而非 killed**：拿掉呼叫或改成 `if (false)` 會讓符號變孤兒（TS6133）或只寫不讀。正確做法是**保留讀取點、只讓條件不成立**（`if (x && false)`、`return f(x) || true`）。
- **註定 survive 的突變要刻意排除**：放進來只會讓 killed 比例看起來有缺口卻無從修。搭配的是把「測不到」誠實寫進原始碼註解與閘門註解兩邊——見下方〈測不到的純防禦碼〉。
- **驗「無界重試」這類缺陷時，突變要用「放寬上限」而非「拿掉上限」**：`scripts/mutate-gate.mjs` 的 `run()` **沒有 timeout** ∴ 會掛住的突變體會拖死整個突變測試。並把便宜的原始碼斷言排在會掛住的端到端斷言之前，讓突變快速紅燈。

## Harness 慣例：mutate-gate 只認特定紅燈行

`scripts/mutate-gate.mjs` 只認輸出含 `❌` 或 `[FAIL]` 的紅燈行——「只丟例外不印標記」的閘門會被判成 **false-kill**。harness 註解明訂的處置是**讓閘門去符合慣例**（改成收集全部失敗再 `exit 1` 並印 `❌`），不是放寬比對。

⚠️ **錨點只驗第一個字面值**：錨點稽核對串接字串只驗第一個字面值 ∴ 多行錨點的「全部找得到」是部分空轉。錨點要寫成**單一字面值**，而真正的證據是 mutate-gate 實跑。

## 順序型承重不變式的三件套

當要保護的是「A 必須排在 B 之前」這類順序不變式，三件套缺一不可：

1. **模組契約測試** — fake api 記錄 send/edit/delete 呼叫序列
2. **來源順序斷言** — `indexOf(A) < indexOf(B)`，錨在該呼叫點**獨有**的字串上避免多處 match
3. **mutation test** — 手動把呼叫搬到錯位置確認測試真的紅，再還原並 `git diff` 確認無殘留

這三件套是對抗恆真斷言的具體做法。

## 測不到的純防禦碼（2026-08-18）

`src/preamble-secret-scan.ts:98` 的 `re.lastIndex = 0` 經實測：從 dist 移除仍 34/34 全綠——下面的 while 迴圈一定跑到 `exec` 回 null，而帶 `/g` 的正則對 `exec` 回 null 時本來就會自動歸零 `lastIndex` ∴ **在現行程式碼形狀下觀察不到**。

三個處置**合起來**才完整：
1. 原始碼註解誠實標明「這行沒有任何測試蓋得到，它是純防禦」並寫清楚它保護的是未來（迴圈裡加一個提早 `break`，跨呼叫的 `lastIndex` 污染就變真的漏報）
2. 對應斷言標明自己**過度決定**（BC-4「冪等」看起來像在守它、實則殺不掉這個突變，斷言名稱直接寫「不守 lastIndex」）
3. 突變清單刻意排除註定 survive 的突變

面對不可測的防禦碼，正解不是刪掉也不是硬湊假守衛，是把「測不到」同時寫進原始碼與閘門註解兩邊。

## 機械閘門守不住的：「這條建議是不是猜的」

為排除法建議加的斷言 `direct.includes("排除法")` 被跨 vendor 覆核當場構造出反例——一條同樣寫成排除法形式的**新**錯誤歸因照樣全綠（2026-08-19）。這類斷言只能寫成「驗形式」（含某字樣、條目數、格式一致），**不可寫成「驗它不是猜的」**。這是突變測試的能力上限：突變能證明斷言會紅，不能證明斷言驗的是對的東西。
