Executive Summary

A2A (Agent-to-Agent Protocol) 是 Google 於 2025 年 4 月發布的開放協定，目標是讓不同框架、不同供應商的 AI agent 能夠安全地互相發現、溝通與協作，無需共享內部工具或 prompt。

核心定位是 agent-to-agent 水平協作（peer-to-peer），與 MCP 的 agent-to-tool 垂直整合互補。對 telegram-kiro-bridge 而言，可借鏡 Agent Card 自描述格式與 INPUT_REQUIRED 中斷態概念，但不建議完整採用——bridge 的 specialist/relay 在單一信任域內，A2A 的複雜度過高。

1. 核心概念

1.1 設計目標

  • 互操作性：讓異構 agent 系統（不同框架、不同模型）能協作
  • Opaque Execution：agent 不需暴露內部工具或 prompt
  • 安全邊界：跨組織協作時保護各方知識產權

1.2 四大抽象

概念 說明 類比
Agent Card JSON 格式的自描述文件，列出 agent 的名稱、能力、支援的輸入模式、認證方式 履歷表 / API spec
Task 有狀態的工作單元，生命週期：submitted → working → input-required → completed/failed/canceled 工單 / Issue
Message / Part 任務中的對話訊息，Part 支援多模態（TextPart、FilePart、DataPart） 聊天訊息
Artifact 任務產出物，可包含檔案或結構化資料 交付物

關鍵洞察：三者互補非競爭。A2A 解決「不同團隊的 agent 如何協作」，MCP 解決「agent 如何存取工具」，ACP 解決「如何控制 agent」。

2.3 決策規則

何時需要 A2A：跨信任邊界的獨立 agent 協作（不同公司、不同團隊、需保護內部實作）

何時不需要：同一團隊擁有的 agent，用 orchestration framework 即可

3. 技術細節

3.1 Agent Discovery

  • Agent Card 發布於 /.well-known/agent-card.json
  • 支援 registry 集中註冊（類似 DNS）
  • client 可根據 skills 欄位判斷 agent 能力

3.2 Task 生命週期

submitted → working → [input-required ↔ working] → completed | failed | canceled
                ↑                                              |
                └──────────────── (resume) ────────────────────┘

input-required 是關鍵狀態——agent 可暫停等待 client 提供更多資訊，而非強迫一次給完所有輸入。

3.3 通訊協定

層級 協定
Transport HTTP/HTTPS
Messaging JSON-RPC 2.0（也支援 gRPC、REST）
Streaming Server-Sent Events (SSE)
Auth OAuth 2.0、API Key、JWT

3.4 核心 RPC 方法

方法 用途
tasks/send 建立任務並送出訊息
tasks/get 查詢任務狀態
tasks/cancel 取消任務
tasks/sendSubscribe 建立任務並訂閱 streaming 更新
tasks/resubscribe 重新訂閱既有任務

5. 借鏡評估

5.1 可借鏡

✅
Specialist 自描述格式

目前 SpecialistConfig 只有 description 字串，可擴充為類似 Agent Card 的結構（skills、inputModes、tags），讓 main agent 的 specialist 選型更有依據。

✅
INPUT_REQUIRED 中斷態

目前 delegate 是 fire-and-forget，無中途互動。可考慮讓 specialist 回傳 { status: 'input-required', message: '...' }，支援「需要更多資訊」的情境。

✅
contextId 顯式化

目前 chatId 隱式作為 context。若未來支援跨 chat 的 long-running task，可加入顯式 contextId。

5.2 不建議採用

❌
完整 A2A 協定

Bridge 的 specialist/relay 在單一信任域內，A2A 的 opaque execution 保護不必要，HTTP+JSON-RPC 的複雜度過高。

❌
JSON-RPC/gRPC/REST 多綁定

Bridge 只需要一種通訊方式，三套綁定增加維護負擔無實質收益。

❌
標準 Agent Card 發布

/.well-known/agent-card.json 需要 HTTPS 公開端點，bridge 目前是私有部署。

5.3 結論

建議策略：從 A2A 借鏡概念（Agent Card 結構、INPUT_REQUIRED 狀態），但不採用完整協定。Bridge 的 specialist/relay 架構已能滿足單一信任域內的 agent 協作需求。
