# 剝註解 fixture 行號空洞修正後的重跑（2026-08-12）

## 這輪改了什麼

上一輪（`arm-test2`）的「剝註解」對照組保留原始行號、只抽掉註解行與空行 ∴ 行號不連續。
兩個模型都把空洞讀成「有程式碼被刻意隱藏」並開始推測那幾行的內容，漏報被系統性放大。

`arm-test3` 的**唯一**變更：nocmt 剝完註解後**連續重編行號**
（`lines.map((e,i)=>({...e, n: site.from+i}))`）。strip 邏輯與 prompt 逐字節不動。
∴ 兩組比較各只差一個變因：

| 比較 | 差異 | 量的是 |
|------|------|--------|
| old-orig vs new-orig | **無**（同條件重跑） | test-retest 翻轉率 |
| old-nocmt vs new-nocmt | 只差行號連續性 | 修洞效果 |

突變行的**渲染後行號**由 replace 位置直接算出並寫進 JSON 當 ground truth
（不事後用字串搜——S2 的 `active--;` 錨點不唯一，事後搜必錯）。
16 個 cell 的 dry-run 自檢：GT-OK ＋ 行號全連續。

## 評分判準（old 32 筆與 new 32 筆在**同一輪**下重評）

命中 = ①引用的行號落在突變行（刪除型突變放寬 ±2 行）**且** ②說對失效機制
**且** ③結論主張它是缺陷（明說「不構成缺陷／沒有缺陷」即使指對位置也算漏報）。

⚠️ 這把尺與上一輪 session 當下用的尺不同 ∴ **絕對數字不可與先前記錄的 9/16、6/16 對照**。
下表 old 與 new 都是這把尺重評的結果，彼此可比。

## 結論一：test-retest 翻轉率 25%，這條 gate 掉其他一切

orig 條件**什麼都沒改**，重跑後：
- sonnet 4/8 → 6/8（S2、S7 由 M 翻 H）
- opus 3/8 → 5/8（S5、S6 由 M 翻 H）

**16 個同條件 cell 翻了 4 個＝25%**，且四次全部同方向（新批次較高）。
同向的機率若純為隨機是 2×(1/2)⁴ = 0.125（不顯著，但值得警戒：可能是運氣，
也可能是伺服器端版本／負載之類的批次效應——本實驗**無法區分**）。

⇒ n=8 的一臂，光噪音就有約 ±1.4 題的擺盪。**先前所有「orig vs nocmt」「sonnet vs opus」
的差值都在這個噪音帶之內** ∴ 那些差異不能當成訊號讀。

## 結論二：修洞沒有換到可辨識的 nocmt 改善

- sonnet nocmt 2/8 → 4/8（+2）
- opus nocmt 2/8 → 2/8（±0）

但同一批 orig 在零改動下也各 +2 / +2。**nocmt 的提升完全落在同批 orig 的漂移量之內**
∴ 量不出「修掉行號空洞」本身帶來的改善。修正在方法論上仍是對的（移除了一個已知偽影），
但它不是先前 nocmt 表現較差的主因。

## 結論三：偽影本身確實消失了（陽性對照通過）

S7-nocmt 的 sonnet：
- 舊：「行 289–290 未附上」「若那段 code 根本不存在」——**虛構片段內部被隱藏的行**
- 新：「那個分支不在這段程式碼裡」——推論的是**片段邊界之外**的碼

內部空洞的虛構消失了；邊界外的推測仍在，但那是合理的（片段確實從函式中間開始）。
兩者都仍導致 S7 漏報 ∴ 偽影不是 S7 漏報的唯一成因。
另：nocmt 的直接棄答仍在（新 S1/S6 的 sonnet 都答「沒有缺陷」）。

## 結論四：註解效應在修洞後仍是同方向，但仍不顯著

新批次：orig 11/16 vs nocmt 6/16。配對來看 7 對不一致，6 對偏有註解、1 對偏無註解，
精確二項雙尾 p = 0.125 → **不顯著**。分模型：sonnet 4 對不一致（3 偏 orig，p=0.625）、
opus 3 對不一致（3 偏 orig，p=0.25）。

有價值的是**機制證據**而非計數：兩處模型逐字說出自己是靠註解與碼的矛盾找到缺陷——
- S2 opus：「諷刺的是，註解（行 12-15）描述的正是這個問題並聲稱透過『直接交棒』解決，但實作並沒有做到」
- S5 opus：「註解說『用 function replacer』，而程式碼用的是 `.replace(regex, v)`……這與註解聲稱的防護不符」

這是「覆核者在比對註解與碼的矛盾、而非從碼推導缺陷」的一手證據，且是在偽影移除後取得的。

## 結論五：sonnet-4.6[max] vs opus-4.5 仍量不出差別

新批次 sonnet 10/16 vs opus 7/16。配對 McNemar：3 對不一致、全部偏 sonnet，
精確雙尾 p = 0.25 → **不顯著**。加上 25% 的 test-retest 翻轉率，這個差距沒有解讀價值。
（不可把 old 與 new 併池——同一批題目量兩次，不獨立。）

## 兩個站點是「碼內自相矛盾」，與註解無關

S4（`results.set(ready[i], …)` 旁邊三行都用 `runnable[i]`）與 S8（`started++` 有、
`finished++` 沒有）在四個 batch×variant 組合下 **8/8 全中**。這類缺陷不需要註解、
也不需要跨檔上下文，模型穩定抓得到。相對地 S1（`max` 少夾下界）**16/16 全漏**——
兩臂在該站點一律改談 semaphore 交棒樣板，與眼前的碼無關。

## 評分器自身的坑（記下來，下次別再踩）

行號抽取一開始只認 `行 N` / `第 N 行`，讀真實回答才發現漏了兩種格式：
`584–587行：`（數字在前、無前綴）與 `124–131：`（純數字範圍加冒號）。
這造成 2 筆**假漏報**。pattern 型斷言的鑑別力必須用真實樣本驗，不能憑想像列舉格式。

使用者在三個選項（收線／加大 n／改行為測試軸）中選了行為測試軸。

## 關鍵發現：這 8 個變異本來就出自 `scripts/mutate-gate.mjs`

前一輪的 fixture 是「真實 mutate-gate 變異」∴ repo **已經**為它們全部寫了行為閘門。
不需要重建任何東西，直接跑就有對照：

| S8 | `started++` 有、`finished++` 沒有 | **8/8** | M3 | ✅ killed |

**8/8 killed，且每條都紅在目標 check**（mutate-gate 三層判定的第②層——只看 exit code 會把
「腳本在更早的 section 就崩掉」誤讀成 killed）。

## ⚠️ 這個對照能宣稱什麼、不能宣稱什麼

**不能宣稱**「行為測試比模型會找 bug」。閘門是**為這些變異寫的**，模型是冷讀 ∴ 8/8 是構造上的，
不是競賽結果。這個設計**完全不測**「發現未枚舉缺陷」的能力。

**能宣稱**的是另一件事，而且它才是決策相關的：

> 對**已枚舉**的缺陷，行為測試給確定性偵測；模型審查給 0–100%（依缺陷型態而定），
> 外加 25% 的 run-to-run 噪音。

## S1 是決定性的那一格

`const max = Math.max(1, Math.floor(limit) || 1)` → `const max = limit`：

- **模型**：16 個回答**全部**漏掉，而且**全部**在同一個檔案上誤報了另一個不存在的缺陷
  （semaphore「waiter 沒有 `active++` 會超上限」——那是直接交棒的設計，本來就不該變）。
  同一格同時是 100% 漏報與 100% 誤報。
- **閘門 J2**：`❌ limit=0 仍拿得到位子 — got=stuck`。實際建一個 `limit=0` 的 semaphore、
  觀察 acquire 是否 resolve。二元、確定、零解讀空間。

∴ **可操作的判準**：缺陷若「與標準樣板同形、但參數處理被動過手腳」，模型覆核的期望值是 0，
加派覆核者不會改善（兩臂犯完全相同的誤報＝同源天花板）。這類不變式**必須**有行為閘門。

反面同樣可操作：S4／S8 這種「碼內自相矛盾」（相鄰三行用不同陣列、計數器只增不減）模型 8/8 全中，
是覆核的甜蜜區——這類不需要優先寫閘門。

## 順帶：給 mutate-gate 加了 id 篩選

複驗單條變異原本得整集跑（8 條目標散在 4 集共 56 條，每條一次 tsc + gate ≈ 25 分鐘）。
加了可選第三參數：`node scripts/mutate-gate.mjs job-orchestration-p1 J2,J7`。
**id 打錯一律 exit 2**——不可讓它安靜跑 0 條印出「0/0 killed ✅」，那正是這支腳本存在的理由
所要消滅的恆綠假象。已驗：`check-mutation-anchors.mjs` 對 327 條錨點仍全數解析成功。
