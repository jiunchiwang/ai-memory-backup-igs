# MCP 無 type 參數被當字串送

## 概述

MCP 工具的參數 schema **沒宣告 `type`** 時，部分 client（實測含 Claude Code）會把你寫的參數值**當純文字**送過去，不做 JSON 解析。於是你以為在送物件：

```
value = {"refNodeUuid":"c1Hlk034NKga7Z4e0mgn0g"}
```

工具收到的其實是那 41 個字元的**字串**。它的「物件 → 特殊處理」分支永遠不會觸發，落到 fallback（多半是「assigned as-is」）原樣存下來，而且**照樣回 `ok: true`**。

⚠️ **這不是工具的 bug**。同一個工具從會送真 JSON 的 client 呼叫就正常。把它當成「這個 MCP 壞了」去回報，作者會（正確地）說「應該是正常的」，然後你得從頭重驗一次。

## 何時使用

- MCP 工具回 `ok: true` / `applied`，但事後讀檔發現值是**字面 JSON 字串**（`"{\"x\":1}"` 這種）
- 傳「物件形」參數（node/資源參考、座標、巢狀 config）沒生效
- 準備跟工具作者說「這個 tool 壞了」之前
- 同一個 MCP server，有些工具傳物件正常、有些不正常

## 不要用在

- 工具回**明確錯誤**（`ok: false`、丟 exception）：那是真的失敗，照錯誤訊息查
- 參數 schema **有**宣告 `type: "object"` / `"array"` 卻仍失敗：不是本 skill 的成因，往工具邏輯查
- 純 read / query 類工具：沒有寫入，看不到這個症狀

## 診斷三步

### 步驟 1：空白指紋 —— 判斷工具收到的是字串還是物件

**最快、幾乎免費**。用**兩種排版**送同一個語意的值，然後比對落地內容：

```
第 1 次： {"refNodeUuid":"AAA"}      ← 冒號後無空格
第 2 次： {"refNodeUuid": "AAA"}     ← 冒號後有空格
```

- 落地內容**照抄你的空白**（一次沒空格、一次有空格）→ 工具收到的是**字串**。物件經過 `JSON.stringify` 會正規化，不可能保留你的排版。
- 落地內容**兩次一致**（都被正規化）→ 工具收到的是物件，成因在別處，本 skill 不適用。

### 步驟 2：typed-vs-untyped 對照 —— 證明是 schema 不是 client 能力

在**同一個 MCP server** 找一個參數 schema 有宣告 `"type": "object"` 的工具，送巢狀物件過去：

| 工具/參數 | schema | 送巢狀物件 | 結果 |
|---|---|---|---|
| `A.value` | **無 `type`** | `{"refNodeUuid":"…"}` | 原樣字串 ❌ |
| `B.props` | **`"type":"object"`** | `{"position":{"x":11,"y":22,"z":33}}` | 真的物件 ✅ |

有 type 的通、沒 type 的不通 → **client 送得出物件，缺的是 schema 的 type 宣告**。這一步是決定性的，沒做就不要下結論。

### 步驟 3：讀回驗證，不信任回傳值

`ok: true` 在這個失敗模式下**一定**是綠燈。唯一可信的是讀目標本身：檔案、`git show`、執行期實際物件。設完就讀回。

## ⛔ 一個會把你帶錯路的假陽性

在**無 type 的參數**上送**數值**，落地常常是正確的數字：

```
value = 0.75   →   檔案裡是 0.75（數字，不是 "0.75"）
```

很容易推論成「數值有正常轉型 ∴ client 沒把值字串化 ∴ 是工具壞了」。**這個推論是錯的。**

真相是：client 送了字串 `"0.75"`，是**下游**（工具、或目標屬性的型別系統）把它轉成 Number。目標屬性是數字型別就轉得掉，是物件/參考型別就轉不掉。

∴ **只有物件形參數能當證據**。用純量測出來的「成功」不算數。

## 對策（依優先序）

1. **換一個 schema 有 type 的同功能工具**。同一 server 常有多條路徑做同件事。
2. **繞過工具層直接改目標的原生序列化，再叫 server 重載**。目標是檔案時最實用 —— 用該格式原生的參考寫法，不要用工具的中介格式。
   - Cocos 3.x prefab/scene 的同檔 node 參考是 `{"__id__": N}`（N = 該 node 在 JSON 陣列裡的索引），不是 `{"refNodeUuid": "..."}`。改完跑 `asset_reimport`，再開執行期確認參考真的解析得到。
   - 改前先確認檔案已 commit，這樣搞壞可以 `git checkout --` 還原。
3. **回報作者，附步驟 2 的對照表**。可提的具體修法：
   - 給該參數補型別（`"type": ["object","string","number","boolean"]` 或 `anyOf`）——沒 type 的參數在部分 client 會被當純文字送
   - 或工具端對 string 型的 value 先試 `JSON.parse`，解得出預期形狀就走對應分支
   - 或設定後讀回驗證再回報，不要無條件 `ok: true`

## Common Mistakes

| 錯誤 | 修正 |
|---|---|
| 看到值變成字面字串就下結論「這個 MCP 壞了」 | 先做步驟 2 的 typed-vs-untyped 對照。沒對照就是猜 |
| 用「數值有正常轉型」證明 client 沒字串化 | 假陽性（見上節）。只有物件形參數算證據 |
| 信任 `ok: true` 就往下做 | 這個失敗模式一定回綠燈。設完必讀回 |
| 回報作者時只說「不能用」 | 附 schema 有無 type 的對照表 + 空白指紋，作者才定位得到是 interop 不是邏輯 |
| 用工具文件寫的中介格式（`{refNodeUuid}`）去手改檔案 | 那是工具的輸入格式，不是檔案格式。要查目標格式的原生參考寫法 |
| 手改檔案前沒先 commit | 做壞了沒有還原點。這類實驗一定要有 `git checkout --` 可退 |
| 手改完只看檔案內容就宣告完成 | 檔案對 ≠ 執行期參考解析得到。要開執行期讀實際物件 |
| 實驗把檔案改壞後忘記還原 | 探測性實驗一律「測完立刻還原 + 讀回確認還原成功」 |
