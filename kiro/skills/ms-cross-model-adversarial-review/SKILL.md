# 異源對抗覆核（push 前的第二雙眼睛）

## 概述

自己審自己有一個結構性天花板：**同一個腦袋寫的註解、commit message、文件、測試敘事互相印證，只是回音不是驗證。** 三處都說同一件事，不代表那件事是真的——只代表它們同源。

異源覆核（換一個模型、給它乾淨 context、要它讀原始碼）打破的正是這一層。它不是「多一輪檢查」，是**換一個可能犯不同錯的觀測者**。

核心原則：**開放授權不給檢查清單；要它讀碼不信敘事；findings 不照單全收，每條自己重現後才動手。**

## 何時使用

- 有未 push 的 commit，改動碰到承重路徑（熱路徑順序、介面契約、cancel/finalize 時序、第三方依賴決策）
- 剛做完 merge / upstream sync，要 push 到共用 remote 之前
- 寫了一批「因為 X 所以 Y」的註解 / commit message / 架構文件
- 高風險的認知性產出（方法論修改、事實主張、依賴取捨論證）
- 自審已經找不到東西了——那正是最該找異源的時候

**不要用在：**
- 微小改動（typo、設定值、單檔 <50 行）——覆核 overhead 比改動本身大
- 純機械重複（rename、格式化）——型別系統與 lint 已經是異源
- 取代自己的驗證：覆核是**疊加**在 tsc / 測試 / 自審之上，不是替代

## 不要把覆核自動化成無條件停止閘門

覆核是**點名制**，不是**全站掃描**。看到 CLI 提供「stop 時自動跑異源覆核」的 hook 會很想開——這裡是實測過的反例。

以 Codex Claude Code plugin（`codex` 1.0.4）的 `--enable-review-gate` 為例，讀 `scripts/stop-review-gate-hook.mjs` 的實際行為：

**1. 沒有 diff 閘門。** `main()` 在 gate 開啟且 Codex 可用時，**直接**呼叫 `runStopReview()`，中間沒有任何「這輪有沒有改到程式碼」的判斷。所以觸發單位是**每個 turn**，不是每個任務——純文字問答、一句「謝謝」，照樣跑一次完整覆核。

**2. 失敗一律 block，不是降級放行。** 只有回應第一行是 `ALLOW:` 才放行；以下全部 `decision: "block"`：

| 情境 | 結果 |
|---|---|
| 覆核者回 `BLOCK:` | block（這才是設計意圖） |
| task 失敗（額度耗盡、429、網路） | **block** |
| 15 分鐘 timeout | **block** |
| 空輸出／非 ALLOW/BLOCK 開頭 | **block** |

後三種的 block 理由跟你的程式碼品質**完全無關**。額度一撞牆就進入「每次想停下來都被擋住」的迴圈。

**3. 成本被 agentic 工具迴圈放大。** 實測給 Codex 一個近乎零工作量的任務（讀兩個檔、引用 15 個字元）花了 **47k tokens**。帶 diff 的真實覆核只會更高，再乘上「每個 turn 一次」。

判準：

- **免費／有限額度方案 → 一律不開。** 額度耗盡的懲罰是 block，不是靜默跳過。
- **付費且工作型態是長時間連續改碼 → 才值得評估**，且要先確認該 hook 有 diff 閘門、失敗時是 warn 而非 block。
- 兩個條件都成立之前：**手動點名**（本 skill 的「何時使用」那份清單就是點名判準）。

這條跟前面的成本分級同源——覆核者是稀缺資源，浪費在「這輪根本沒改到碼」上，跟用最強模型去審 typo 是同一種浪費。

## 覆核者選型（成本分級）

異源性來自「**不同模型 + 乾淨 context + 自己讀碼**」，**不是**來自「用最強的那個」。最強模型只在需要長推理鏈的 finding 類型上才拉開差距——其餘一律降級，因為覆核者是 agentic 的（實測一次 37 次工具呼叫、587 秒，讀進去的碼全算 input），單價會被工具迴圈放大。

Claude 家族單價（來自 model catalog 的 `pricing` tier，`tier_A_B` = $A/M input、$B/M output）：

| 模型 | tier | 相對成本 |
|---|---|---|
| Haiku 4.5 | `haiku_45` | ~0.3x |
| Sonnet 5 | `tier_3_15` | 1x |
| Opus 5 | `tier_5_25` | 1.7x |
| Fable 5 | `tier_10_50` | **3.3x** |

按 finding 類型選：

| finding 類型 | 選誰 |
|---|---|
| 孤兒 import / 死碼 | **不派人**——交給型別系統（TS 開 `noUnusedLocals`；其他語言用等價 lint） |
| 敘事與碼不符（註解／commit／文件） | Sonnet 5——這是比對工作，不需長推理 |
| 恆真斷言 / 閘門強度低於宣稱 | Sonnet 5 |
| **不變式**（集合包含關係、單調性前提） | 最強（Fable 5） |
| **論證推理缺陷**（依賴取捨、風險評估） | 最強（Fable 5） |
| **時序 / cancel-finalize race** | 最強（Fable 5） |

判準一句話：**改動碰承重路徑（時序、不變式、跨模組契約、依賴決策）→ 最強模型；其餘 → Sonnet 級。**

兩個額外的省法（不動紀律結構）：
- **給地圖不給答案**：直接餵 `git show <commit>` 的 diff 全文 + 涉及檔案清單當**起點**，省掉盲找的工具迴圈。這不違反「開放授權不給檢查清單」——給的是哪些檔案被動到，不是要檢查哪幾點。
- **收斂條件按嚴重度分岔**：第一輪只出 low／敘事類 → 修完直接 push；第二輪只在第一輪出過 high/medium 時才派。

不要為了省而砍掉的：開放授權那句、每條 finding 自己重現、承重 commit 的第二輪。

## 覆核 prompt 的四條規則

| 規則 | 為什麼 |
|---|---|
| **給開放授權，不給檢查清單** | 清單會限縮它的視角，它只會回答你已經想到的問題 |
| **明確要它讀原始碼**，不要信 commit message / 註解 / AI.md 的自我描述 | 那些正是可能被同源污染的東西；覆核最有價值的 finding 常常就是「你的敘事跟碼不符」 |
| **明確授權它說「已收斂」** | 不然它會為了交差硬湊 finding；連三輪都能生出 finding 本身就是可疑訊號 |
| 若一定要給檢查面，**至少一項要問成開放式的互動問題** | 「這條回傳值在所有錯誤路徑上都對嗎」會逼它去枚舉；「確認我的 X 宣稱正確」只會得到附和 |

第 4 條是 2026-07-31 的實測修正：清單式 prompt 並非全無用——它照樣抓到了同源自審漏掉的 medium 缺陷，關鍵在於問法是開放的還是確認式的。

## Findings 處置流程

**不照單全收。** 實測命中率大約 6–7 成（4 條中 3 成立、7 條中 5 成立），而且覆核者自己也會枚舉不全、也會判斷錯。

```
對每一條 finding：
├─ 讀原始碼／造反例，自己重現
│   ├─ 重現成功 → 修
│   ├─ 重現失敗 → 駁回，並在回報裡寫明「為什麼不成立」
│   └─ 「潛在弱點非現行 bug」類 → 必須造出反例才算成立
├─ 修完用「原本能重現的同一組反例」驗不再重現
└─ 補正向迴歸（別過度修正：收緊 regex 可能連真的命中也一起排除）
```

修 findings 的過程本身會引入新問題——實測有一輪連踩三個（黑名單漏掉 `}` 與 `<`、漏掉第三個註冊面、警告輸出讀錯欄位），**全部靠檢視輸出內容才發現，只看 exit code 一個都看不到**。

## 多輪、範圍逐輪收窄

一輪不夠。每修完一輪就對**新 commit** 再派一輪範圍限定的覆核：

```
round 1: commit A + 工作區  → findings → 修 → commit B
round 2: 範圍只限 commit B  → findings → 修 → commit C
round 3: 範圍只限 commit C  → 只剩敘事精確度類 → 收斂，push
```

收斂條件：**只剩「敘事精確度」類 finding、無行為 bug**。繼續下去是遞減報酬。

反過來說：修「註解與碼不符」的那個 commit，本身又埋了同型的錯——這在實測中真的發生了（第二輪抓到修正版又寫錯，第三輪抓到錯長在測試敘事裡）。所以「我剛修完這類問題」不是跳過下一輪的理由。

這個「往上層遷移」不限於 2 層。2026-08-06 的一次實測連續遷移了 4 層：碼裡的 hint 字串硬編 → 靜態文件（SKILL.md）與碼矛盾 → 另一份靜態文件（DESIGN.md）的錯誤值清單漏舉 → 列舉完整性（有 error 值三份文件都沒提）。每一層都是異源在下一輪抓到，而自己每輪都判斷「這輪應該只剩敘事精確度」——直到真的碰到那一層才發現還有下一層。層數沒有上限，收斂判準要看的是「這輪還有沒有新類型的 finding」，不是「已經修過幾輪」。

## 異源結構上才抓得到的類型

值得為這些特地派覆核：

| 類型 | 為什麼同源抓不到 |
|---|---|
| **因果敘事與實際時序不符** | 註解／commit／文件三處都是你寫的，互相印證只是回音 |
| **枚舉半途而廢** | 你以為掃完了；實際上搜尋詞是中文，漏掉英文寫法的那一處 |
| **恆真斷言 / 閘門強度低於宣稱** | 你寫的斷言，你也覺得它在驗東西（見 ms-vacuous-test-gate） |
| **孤兒 import / 死碼** | `tsc` 全綠不代表沒有——`noUnusedLocals` 沒開的話型別系統看不到 |
| **論證的推理缺陷**（依賴取捨、風險評估） | 你的結論和你的前提是一起長出來的 |

## 覆核也可能往安全方向推翻你

不要只預期它「增加工作量」。實測有一次結論是反向的：我擔心新加的強制補送會打穿 429，它指出**舊碼**在某個階段節流時間戳從不更新、原本的 1200ms 節流一直是失效的，新碼反而把尖峰壓回節奏內——所以「樣本太小」的疑慮根本不需要處理，結構性風險本來就沒上升。

同理，它的「已窮舉」宣稱也要驗：它說「全庫只有 5 條出口」時，自己 grep 一次確認。

## Common Mistakes

| 錯誤 | 修正 |
|---|---|
| 用「自審已找到 N 條，覆蓋了」跳過異源覆核 | 自審的 N 條與異源的類型不重疊；這是 hard requirement 不是加分項 |
| 給覆核者一份檢查清單 | 開放授權；真要給檢查面，至少一項寫成開放式問題 |
| findings 照單全收就開始改 | 每條自己重現；駁回的也要寫明理由 |
| 只看 exit code 確認修好了 | 檢視輸出內容——修 findings 過程引入的新問題只在輸出裡看得到 |
| 一輪覆核就 push | 修完再派一輪範圍限定的；直到只剩敘事精確度 |
| 覆核者說「可以 push」就 push | 那是針對**它看過的那個 commit**；你修 findings 後產生的新 commit 沒被看過 |
| 把覆核者的「已窮舉」當事實 | 自己 grep 一次；覆核者也會枚舉不全 |
| 覆核完把 findings 丟掉 | 未採納的寫進 commit message；低優先的列成 follow-up，不要靜默消失 |
| 開啟 CLI 的 stop-time 自動覆核閘門 | 先讀該 hook 的實作：有沒有 diff 閘門？失敗是 warn 還是 block？多數是「每 turn 觸發 + 失敗即 block」 |
