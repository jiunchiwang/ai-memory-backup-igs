# 黑箱探針實驗設計（對文件不說的行為量出答案）

## 概述

有一類問題不能靠讀文件解決：API 永遠回傳 200、client 端 UI 行為沒有官方規格、第三方服務的副作用在文件裡是空白。你只能設計實驗去問它。

但「多跑幾次看看」不是實驗——**缺乏對照的觀測是零資訊量的**。全負結果可能是「假說錯」，也可能是「觀測方法根本無效」。你需要一個已知會紅的臂來區分這兩種情況。

核心原則：**陰性對照必須有效、observable 必須對齊症狀、內容相依時不可固定內容。**

## 何時使用

- 診斷 Telegram draft 重播、client 端動畫、bot webhook 副作用等「API 回傳成功但行為不符預期」
- 設計多臂實驗去二分「是 A 還是 B 造成的」
- 探針全負但不敢下結論（擔心觀測方法有問題）
- 探針結果與先前假說矛盾（同樣的碼，這次結果不同）
- 要決定每一臂的參數、判讀表、與「實驗無效」的定義

**不要用在：**
- 可直接讀原始碼或文件確定行為的問題
- 一次性手動測試（沒有「未來要重跑」的需求）
- 單一變數、不需要對照的簡單驗證

## 設計原則（已付代價的教訓）

### 原則 1：陽性對照必須有效

> 對照失效時，陰性結果 ≠「假說錯」，= 「這個問法問不出東西」

**踩坑實例**（2026-07-31 draft 重播探針）：
- 三臂探針測「sendMessage 是否清掉 live draft」，全部不清（陰性）
- 但事後發現陽性對照（臂 A：draft 存在後直接查詢）**本身就是陰性情境**——draft 根本沒在預期時間出現
- 結論：三臂實測結果全部作廢，因為無法區分「sendMessage 不清 draft」與「draft 從來沒建立」

**防範**：
1. 每個探針必須至少有一臂是「我知道它會紅」的陽性對照
2. 陽性對照失敗（應該紅卻綠）→ 立即停止，不繼續解讀其他臂
3. 陽性對照的「紅」必須走跟其他臂**相同的觀測路徑**

### 原則 2：Observable 必須對齊症狀

> 問的問題必須跟使用者報的症狀是同一件事

**踩坑實例**（2026-07-31 draft 重播探針）：
- 我問的 observable：「draft 是否消失」
- 使用者報的症狀：「文字消失後**從頭重播**」
- 結果：我的探針測「消失秒數」，但症狀的重點是「重播動畫」——兩件不同的事
- 探針全負（不消失），但症狀持續存在

**防範**：
1. 開始設計前先用一句話寫出「使用者看到的具體現象是 ___」
2. 確認探針的判讀標準能直接映射到那個現象
3. 如果症狀是「A 然後 B」兩步，探針必須同時測兩步

### 原則 3：內容相依時不可固定內容

> 2×2 設計裡若把一個變數 held constant，你測的就不是完整的組合空間

**踩坑實例**（2026-08-01 draft 重播 2×2 探針）：
```
|                        | 短間隔 (4s) | 長間隔 (20s) |
|------------------------|-------------|--------------|
| append 新內容           | ✅ 測過      | ✅ 測過       |
| 完全相同內容重送         | ✅ 測過      | ❌ 沒測過     |
```
- 生產環境的確切情況是「20s 間隔 + 同內容重送」——正好是右下角那一格
- 先前測 4s 同內容、20s append，各自把對方的變數 held constant
- 漏掉交集，等於沒測到真兇

**防範**：
1. 列出所有可能變數（間隔、內容、順序、數量）
2. 畫出完整的組合矩陣
3. 確認生產環境的確切組合有被覆蓋到
4. 如果無法全覆蓋，優先測生產的確切情況

### 原則 4：全負結果先查有沒有未列出的靜默閘門，才判「假說錯」

> CLI／工具整合類黑箱最常見的陷阱：功能文件上寫存在，探針卻怎麼試都不生效，
> 而失敗**不印任何警告**——因為擋在中間的是一層文件沒提到的信任／權限閘門，
> 不是你要測的那個機制本身沒作用。

**踩坑實例**（2026-08-13 Codex CLI hooks 探針）：
- 假說：`<repo>/.codex/hooks.json` 的 `PreToolUse` hook 會在檔案編輯前攔截
- 前三臂全負（檔案式設定無效、`git init` 無效、真的 `cd` 進專案也無效）
- 逐層拆解才發現**兩道獨立的靜默信任閘門**，且兩道都不印任何錯誤或警告：
  ① 專案要先在 `~/.codex/config.toml` 標記 `trust_level = "trusted"`，否則整個
     `.codex/` 設定（含 hooks）都不會載入；② hook 腳本本身要經過互動式 `/hooks`
     審核信任，否則即使專案已 trusted 仍是 0 捕獲
- 用 `-c` 直接注入設定 + `--dangerously-bypass-hook-trust` 繞開兩道閘門才問出真正答案：
  hook 機制本身是有效的，只是被兩層前提擋住

**防範**：
1. 全負且完全無錯誤訊息時，先問「這個功能有沒有官方文件寫的**啟用前提**（trust／
   權限／設定檔路徑）」，不要直接判「這個功能對我們沒用」
2. 用「繞過所有已知前提」的臂（例如直接用 `-c` 覆寫設定、給最大權限旗標）先驗證機制
   本身有沒有效，再逐一收回前提找出哪一層在擋
3. 同一份探針順手核對**資料形狀**是否符合假說（該實例中還發現 `apply_patch` 的
   `tool_input` 裝的是整段 patch 文字、不是 `file_path`，若假設欄位名稱一樣直接
   重用既有解析邏輯會靜默 fail-open）——形狀錯誤和閘門擋住是兩種不同的全負成因，
   別把兩者混著判讀

## 探針結構模板

```javascript
// scripts/probe-xxx.mjs
// 目的：[一句話描述要問什麼]
// 生產情況：[描述真實環境的參數組合]
// 判讀表：見下方 PLAN

const PLAN = [
  { arm: 'A', role: '陽性對照', params: {...}, expected: '紅', ifGreen: '觀測法無效' },
  { arm: 'B', role: '生產情況', params: {...}, expected: '?',  ifRed: '...', ifGreen: '...' },
  { arm: 'C', role: '排除變體', params: {...}, expected: '?',  ifRed: '...', ifGreen: '...' },
];

// 實作...
```

## 判讀表格式

| 臂 A | 臂 B | 臂 C | 結論 |
|------|------|------|------|
| 紅   | 紅   | 綠   | 兇手是 B 獨有的變數 |
| 紅   | 綠   | 綠   | B/C 共有但 A 沒有的變數排除 |
| 綠   | *    | *    | **實驗無效**（陽性對照失敗） |
| 紅   | 綠   | 紅   | 兇手是 C 獨有的變數 |

## 命名與隔離

- 探針腳本命名 `probe-*.mjs`，刻意不用 `check-*.mjs`
- smoke runner 只掃 `check-*`，`probe-*` 不會被自動執行
- 原因：探針會對真實 chat/資源發送請求，不適合每次 push 都跑

## 實戰案例

### 案例 1：背景通知 flakiness（2026-07-26）

**症狀**：通知固定在 turn 結束後 +3.0s 才到
**假說**：race condition，調整 sleep 會改變時間差
**探針設計**：把 sleep 從預設值縮到 2s
**判讀**：時間差不變（仍是 +3.0s）
**結論**：「調整等待延遲後時間差不變，就不是競態」——排除 race condition，改從通知投遞路徑下手

### 案例 2：Draft 重播根因（2026-07-31）

**症狀**：文字消失後從頭重播，週期固定
**假說 H1**：status bubble 的 editMessageText 清掉 live draft
**八臂探針**：edit 有無、sendMessage 有無、間隔長短、內容變化
**結果**：全負（八臂都不觸發重播）
**問題**：陽性對照臂本身就不紅（draft 在預期時間沒出現）
**實驗狀態**：無效，須重新設計

### 案例 3：Draft 重播 2×2（2026-08-01）

**發現缺口**：4s 同內容測過、20s append 測過，但 20s 同內容沒測
**補測**：P 臂（4s 同內容對照）+ Q 臂（20s 同內容）
**目的**：填滿 2×2 矩陣，確認生產的確切情況

### 案例 4：Codex CLI hooks 靜默信任閘門（2026-08-13）

**症狀**：`.codex/hooks.json` 的 `PreToolUse` 設定怎麼試都攔不到檔案編輯，且無任何錯誤
**四臂探針**：純設定檔 → `git init` → 真的 `cd` 進專案 → 補上 `trust_level=trusted`
**結果**：前三臂全負，第四臂才生效；再拆一層發現還有第二道 hook-hash 信任閘門
**結論**：機制本身有效，只是被兩層文件未強調的前提擋住——見上方原則 4
