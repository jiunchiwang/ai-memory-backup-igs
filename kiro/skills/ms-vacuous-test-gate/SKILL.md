# 綠燈假象：閘門看起來通過但什麼都沒驗

## 概述

一個閘門的資訊量，等於它**有可能紅的程度**。永遠不會紅的閘門和沒有閘門一樣，但外觀跟正常的完全一致——這是它最危險的地方：你以為有防護，實際上防護從第一天就是裝飾。

核心原則：**新增任何斷言之後，必須主動讓它紅一次。沒紅過的綠不是證據。**

## 何時使用

- 剛寫完新的測試斷言 / smoke check / pre-push gate，準備宣稱「已覆蓋」
- 某個 bug 存在很久但測試一直全綠（強烈訊號：那支測試是恆真的）
- 閘門驗的是「數量」「支數」「計數」這類會隨專案成長漂移的值
- 測試用字串錨定（`indexOf(A) < indexOf(B)`）而非行為斷言
- test runner 只印 per-file `ok` / `PASS`，看不到逐條斷言
- 覆核者說「這個斷言不綁 X、強度低於它宣稱的」

**不要用在：**
- 一般測試失敗除錯（那是 systematic-debugging，不是閘門本身有問題）
- 一次性驗證腳本（跑完即丟，不進 CI，沒有「未來會靜默退化」的風險）
- 型別檢查（`tsc` 綠有明確語意，不是恆真問題）

## 五種綠燈假象

| # | 症狀 | 為什麼永遠綠 | 修法 |
|---|---|---|---|
| 1 | **恆真斷言** | 驗「正規化／截斷／clamp 之後的結果符合上限」——那個函式本身就保證上限 | 驗**未經處理的原始值** |
| 2 | **期望值硬寫** | 把支數／筆數寫死在閘門裡；專案一長大，閘門自己就是下一個過期來源 | 期望值**當場向來源取得**（`runner --list`、`Object.keys().length`），零硬寫 |
| 3 | **錨點切太寬** | 「錨點之後第一個 X」——某條 X 被整段拿掉時，會匹配到**下一條**的而放過 | 切片上界收到**下一個錨點**，不是檔尾 |
| 4 | **靠逾時放生** | 測試 harness 的 resolver 被第二次呼叫覆蓋，放走錯的那顆；受測碼其實走 deadline 逾時路徑，斷言仍全綠 | resolver 按 key 存 Map；補**上界斷言**（`elapsed < deadline`） |
| 5 | **runner 只印 ok** | 通過只證明「腳本沒 throw」，不證明新斷言被執行到（可能被 early return 跳過、可能在死碼裡） | **突變測試**（見下節） |

第 2 種有個特別陰險的自我參照版本：**加入這個閘門本身就會改變它要驗的數字**（新增一支 `check-*.mjs` 會讓 suite 支數 +1）。硬寫的話它上線第一天就過期。

第 4 種的判別訊號是**可觀測量**：那支測試的耗時從 0.4s 變成 2.0s，多出來的 1.5s 剛好等於 drain deadline。斷言全綠但時間對不上，時間才是真話。

## 第六種假象：不是恆真，但守錯了性質

上面五種都有一個共同前提——斷言本身**寫錯了、沒真的在驗**。還有一種更難抓的變體：
斷言**確實被執行、確實會紅、突變測試也能證明它有鑑別力**，但它鎖住的行為本身就是錯的。

2026-08-14 實例：一支測試斷言「重送拆成兩則後、前段成功但後段失敗時，把整筆訊息放回
佇列重試」。這條斷言不恆真——突變測試 4/4 killed，改哪個分支就紅在哪個分支。但異源覆核
指出：這個行為本身會造成前段訊息重複投遞（已成功送出的那半又被送一次）。斷言把**這個
錯誤行為**釘成了 expected output，之後任何人想修正這個行為，第一件事就是被這條「證明
有鑑別力」的測試擋下來。

判別法與前五種不同——**突變測試在這裡完全沒用**（它只證明斷言被執行到，證不出斷言
守的性質對不對）。能抓到的只有兩條路：
1. **異源覆核**（見 ms-cross-model-adversarial-review）：讀懂測試在驗什麼安全性質，
   而不是只看它綠不綠。
2. **反向問一句**：「如果這個行為真的發生在生產環境，後果是什麼？」寫斷言時只想著
   「讓這個分支的輸出符合我剛寫的實作」，不會觸發這句反問；事後補問往往就能發現。

## 突變測試（證明斷言真的在跑）

對**每一種預期壞法各做一次最小突變**，不要一次改多處：

```
1. 對受測碼做一個最小突變（改順序 / 改回舊回傳值 / 拿掉守衛 / 拿掉條件的一半）
2. 跑該支測試 → 必須紅，且紅在「對應那一條」斷言上
3. 還原
4. 複驗綠
5. git diff 確認零殘留（最容易忘記的一步）
```

一次一個突變的理由：多個一起改，紅了也分不出是哪條斷言抓到的——可能其中一條仍是恆真。

實際案例（bridge，2026-07-31）：修法有 4 種壞法（順序移回去 / 回傳值改回 false / 拿掉 `|| statusWrote` / 內容不變改回 true），逐一突變 4/4 各自紅、還原後複驗 PASS，才算「新斷言確實在跑」。另一次是把某條 crash handler 的 drain 拿掉 → 逐條斷言精準紅在被拿掉那條，證明它不是只數出現次數。

## 突變體「編譯不過」不等於「killed」

突變測試本身沒問題（會紅、有鑑別力），但**紅的原因**要分辨清楚：如果變異體因為型別系統直接編譯失敗（`tsc` 擋下來），那條不變式是**型別系統**在守，不是你的 gate——把它記成「killed」會高估你這道閘門的實際強度。

2026-08-15 同一天兩次撞到：一次是把新事件型別從型別聯集拿掉（少了它 `tsc` 直接報錯，變異體從沒跑起來過）；另一次是把 `try {` 單獨改掉、留下沒有對應 `try` 的 `catch`（同樣編不過）。兩次的正確處置都是**把突變改成整段替換**（拿掉整個型別/整個 try-catch 區塊），讓它真的跑起來、紅在你的斷言上——如果換了一種寫法後仍然只是編譯失敗，代表**沒有任何行為層面的不變式可測**，這條突變本身該拿掉，而不是留著一條「永遠 error」的項目在總結裡累積噪音。

判別法：突變測試報告如果分「compile error」與「killed」兩種結果，不要把前者算進覆蓋率；如果 harness 沒有分開回報，跑之前先自問「這個變異體會不會連編譯都過不了」。

## 降級既有閘門為 advisory 時，兩個方向都要鎖

當一個硬性閘門被發現量測不準（例如同輸入連跑會翻面的耗時檢查）而裁決降級成 advisory（照樣量、照樣報告，但不再讓 `passed` 變 false）時，只鎖「降級後的新行為」是不夠的——那樣**把整條檢查刪掉**也會通過同一條斷言（`passed` 從此恆為 true，「不再拉低 passed」這個描述完全成立）。

要用兩條斷言分別鎖住兩個方向：

1. **advisory 不再拉低整體 `passed`**（鎖住「降級」這個意圖）
2. **該項目仍然被實際量測、仍然會在自己的欄位裡報告 regression、仍然標著 advisory**（鎖住「沒有被靜默拿掉」）

只寫第 1 條的話，突變測試會漏掉「把整個檢查砍掉」這個最省事、也最危險的回歸——降級的本意是「保留可見性、拿掉否決權」，不是「不管了」。

## 靜態錨定測試的誠實邊界

當受測函式沒匯出、抽出它等於把 refactor 併進 bugfix（風險放大）時，退而用**來源字串錨定**是合理的取捨——但要在註解裡寫清楚它釘的是什麼：

- 釘得住：「guard 存在」「guard 的位置在 A 之後、B 之前」「某呼叫只出現 1 次（上界）」
- 釘不住：runtime 行為、race 是否真的發生
- 脆弱方向：改個變數名就紅（false positive）——這是**安全方向**，不要為了少維護就放寬

「出現次數 === 1」這種上界斷言很重要：少了它，有人把舊的「送完再 update」加回來，順序斷言（只看第一個出現位置）仍然會綠。

## Common Mistakes

| 錯誤 | 修正 |
|---|---|
| 驗 `truncate(x).length <= MAX` | 驗 `x.length <= MAX`（原始值）；前者是函式的定義，恆真 |
| 閘門寫 `assert(count === 93)` | 向 runner 現場取得期望值；新增閘門本身會改變這個數字 |
| 只跑一次確認綠就宣稱已覆蓋 | 至少讓它紅一次；沒紅過的綠不是證據 |
| 一次做多個突變 | 一次一個，且要確認紅在「對應那一條」斷言 |
| 突變測試完忘記還原 | 收尾一定 `git diff`；把驗證用的暫存檔一併刪掉 |
| 第一次突變沒紅就當「等價突變」下結論 | 先確認突變**真的改到了執行路徑**——常見坑是改了 `filter()`／某個中間值，但呼叫端沒有消費那個回傳值，突變等於沒發生（2026-08-13 實例：改 `IsValidReel` 的過濾條件，第一次突變測試仍綠，因為改動的 `filter()` 結果沒被賦值使用；換一個真的會被讀取的欄位重測才紅） |
| 把耗時／效能數字納入閘門 | run-to-run 有數 % 變異，會變成每次都可能紅的雜訊閘；只納入**硬計數**，耗時寫進文件並標量測日期 |
| 彙總式 throw（先 assert 逐條、最後再 throw 總表） | 第一條 assert 就 throw，總表永遠最多一筆 = 死碼 |
| 覆核說「這個斷言強度低於宣稱」就照改 | 先自己造反例重現，確認是真的放過，再改（見 ms-cross-model-adversarial-review） |
| 突變測試 4/4 killed 就宣稱這條斷言沒問題 | 突變測試只證明「斷言被執行到、會紅」，證不出它守的性質是對的——見〈第六種假象〉。改完問一句「這個行為在生產環境發生，後果是什麼」 |
| 突變體因型別系統擋下編譯（`tsc` 報錯）就算「killed」 | 那是型別系統在守，不是你的 gate；換成整段替換讓它真的跑起來，跑不起來就拿掉這條突變 |
| 把硬性閘門降級成 advisory 時只鎖「不再拉低 passed」 | 那樣把整條檢查刪掉也會通過同一條斷言；要另補一條鎖住「仍然被量測、仍然報告 regression」 |
